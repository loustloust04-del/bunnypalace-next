## 一、Onboarding：参考与批判

### 1.1 Minis 的三步引导

用户展示了开源项目 **Open Minis** 的 Onboarding 作为参考案例：

> "欢迎使用 Minis，您的首个本地智能体即将就绪。"
> "1. 添加 AI 服务商 — 配置 API Key 或使用 OAuth 登录 AI 服务商"
> "2. 选择模型 — 请先完成第 1 步"
> "3. 开始对话 — 请先完成第 2 步"

用户明确表示：

> "minis是别人的大项目不是我的！我只是偷学他"

### 1.2 用户提出的引导流程

用户希望设计一套类似的阶梯式引导，但强调**可交互、可跳过、不强迫看说明书**：

> "1，添加provider 2选模型，3，弹出来一个气泡教你写基础提示词 4开始对话。就是这个死步都是可交互的，也可以跳过，产品说明书放doc/内置skill，然后用户可以直接通过跟ai交互的方式学习怎么用（而不是自己去看说明书）"

### 1.3 关于 API 配置的态度

用户不提供内置 API，目标用户需要自备 Key：

> "我又不给他们提供api，难道有人这个都不会配吗"

这意味着 Onboarding 的**第一步是硬性门槛**，也是筛选机制——不会配 API 的用户天然不是目标受众。

## 二、身份选择：比固定步骤更聪明的 Onboarding

### 2.1 核心思路

用户提出用**身份标签**替代单一的线性引导：

> "要不这样，先让人选自己是来干嘛的，：我是小白/我是酒馆用户/我是长期人机关系用户/我是技术用户/保持神秘…然后给相应指引呢？"

### 2.2 不同身份的差异化指引

| 身份 | 需求特征 | 指引策略 |
|---|---|---|
| **我是小白** | 想先聊起来，不想管技术 | 隐藏 API/MCP/正则，提供一键体验或 Demo Key 兜底 |
| **我是酒馆用户** | 有角色卡、有世界观 | 直接导向卡库/世界书，Onboarding 变成"导入你的第一张角色卡" |
| **我是长期人机关系用户** | 要 AI 陪伴、记忆、情感连接 | 强调记忆模块，引导创建第一个长期关系角色 |
| **我是技术用户** | 要调 API、配 MCP、写正则 | 完整版全开，步骤压缩到最少 |
| **保持神秘** | 不想被定义 | 跳过所有引导，扔进主屏，但保留右下角"?"帮助入口 |

### 2.3 提示词教学的交互设计

用户强调提示词教学**不是丢教程，而是 AI 当教练，一步一步带**：

> "写提示词也不是说丢一个教程，肯定是比如说一步一步来，比如配好api，点教我写提示词，然后问你几个问题比如使用场景，格式，do/donot先让ai带着你写一个提示词…"

**理想流程**：
1. **场景提问** — "你想让 AI 帮你做什么？"
2. **格式选择** — "你希望 AI 怎么回复你？"
3. **Do/Don't 提取** — "有什么绝对不能说的？"
4. **生成 + 预览** — AI 拼成 System Prompt，展示给用户
5. **一键应用** — 塞进当前对话或保存为模板

## 三、产品愿景：AI 的 Unity

### 3.1 从 App 到引擎的跃迁

用户提出终极产品方向：

> "其实我想做ai的unity来着"

并强调游戏引擎的哲学价值：

> "不是，你没懂，游戏引擎是最接近模拟创造世界的引擎…"

第二轮补充的用户判断：

> "ai的unity是负债但是未来总会有人做的，app的护城河越来越小，现在代码门槛越来越低，总有人需要定制化"

### 3.2 核心架构映射

将游戏引擎概念映射到 AI 应用：

| 游戏引擎概念 | AI 应用对应 |
|---|---|
| **Scene（场景）** | 世界书 / 对话上下文 / 特定领域的"此刻" |
| **Prefab（预制体）** | 角色卡 / 可复用的 AI 人格模板 |
| **Component（组件）** | 记忆模块、终端模块、朗读模块、MCP 连接器 |
| **GameObject（实体）** | 一个具体的 AI 实例 = 角色 + 能力组件的拼装 |
| **Asset Store** | 模块市场 |
| **ScriptableObject** | 提示词模板 / 正则规则 / 配置文件 |
| **Runtime 生命周期** | 对话状态机 / 记忆持久化 / 上下文管理 |

### 3.3 模块化与市场的野心

用户希望实现社区市场模式（第一轮参照拓竹，第二轮修正为更准确的 Obsidian 模式，见第六节）：

> "我是说模块化组件化，甚至像那个拓竹的网站市场一样，或者大家合作弄一个模块"

## 四、技术架构：ECS + SwiftUI 实现方案

### 4.1 核心分层

```
┌─ 宿主层（Host）─────┐  ← 维护，负责路由/权限/数据
│  主屏框架            │
│  导航与生命周期       │
│  全局状态（用户/主题） │
│  模块市场（下载/安装） │
└─────────────────────┘

┌─ 模块运行时（Runtime）┐  ← 核心，让模块能"活"在宿主里
│  模块注册表           │
│  依赖注入容器         │
│  跨模块通信总线       │
│  安全沙箱（权限隔离）  │
└─────────────────────┘

┌─ 模块层（Plugins）───┐  ← 第三方/社区开发
│  终端模块             │
│  酒馆模块             │
│  记账模块             │
│  背单词模块           │
│  ...                 │
└─────────────────────┘
```

### 4.2 Entity-Component-System 轻量版

- **AIEntity**：一个 AI 实例，动态挂载 Component
- **AIComponent**：能力模块协议（记忆、终端、语音、MCP 等）
- **CharacterPrefab**：角色卡模板，定义默认挂载哪些 Component
- **AIScene**：对话上下文容器，群聊 = 多 Entity + 共享 Worldbook
- **EventBus**：跨模块通信，解耦所有能力

### 4.3 SwiftUI 动态渲染方案

通过 **协议 + 类型擦除 + 注册表** 绕过 SwiftUI 编译时类型限制：

```swift
protocol AIComponent {
    var componentID: String { get }
    func makeConfigView() -> AnyView
    func makeChatView() -> AnyView
}

// 主屏通过注册表动态渲染
ForEach(installedModules, id: \.self) { moduleID in
    if let component = ComponentRegistry.builders[moduleID]?() {
        component.makeChatView()
    }
}
```

### 4.4 模块包结构

```
WordMemory.module/
├── manifest.json          // 组件 ID、版本、依赖、权限
├── assets/
│   ├── icon.png
│   └── preview.jpg
├── prefabs/
│   └── flashcard.json     // 预制体配置
└── logic/
    └── behavior.swift     // 原生逻辑（需编译进主工程）
    // 或 logic.js（走 JSBridge，受限）
```

**注意**：该结构与 Obsidian 插件（main.js + manifest.json + 可选 styles.css）高度同构，验证了方向可行性。manifest 中的**权限声明**从 v0.1 起必填（能否读记忆、能否联网、能否调用终端），权限模型事后补是市场级产品的绝症。

## 五、平台分工：Mac Editor + iOS Player

### 5.1 定位修正（第二轮核心结论）

第一轮的"Mac 引擎 + iOS 终端"在第二轮修正为更精确的 **Editor / Player** 结构——即 Unity 自身的经典分工：

| 平台 | 角色 | 职责 |
|---|---|---|
| **macOS** | **Editor（编辑器）** | 组装 Entity、挂载组件、模块市场的安装与管理 |
| **iOS** | **Player（播放器）** | 运行在 Mac 上组装好的 Scene，面向所有人 |

这一划分顺带绕开了 iOS 平台禁止下载后动态加载原生代码的硬限制：模块只在 Mac 流通，iOS 只消费组装产物。

### 5.2 Mac 引擎化的现实依据

Mac 版不是新造的轮子，而是**已有原生物**（App 原生开发，本就有 Mac 版），只是此前面向普通用户、界面简单。更重要的是，Mac 已经是用户个人 AI 工作流的实际中枢：

> "我连cc和codex都要用mac当hub中转（这样就能吃到oauth的额度）"

即 Mac 已在承担编排中枢职能（为 Claude Code / Codex 做中转），Editor 化是把既成事实产品化，而非凭空增加复杂度。

### 5.3 用户押注苹果生态

> "而且我这个是原生所以有mac版，说实话未来我压苹果生态（如果未来有时间，而且模型又进步了的话，我会搞win/安卓），mac版是引擎"

Win/Android 推迟，但 Win 版未来可作为 Editor 的第二个宿主（"unity=mac（或者win）版"）。

### 5.4 数据同步

**已完成**：iCloud 同步（Mac ↔ iOS 的对话记录、记忆、角色卡流转管道已落地）。

## 六、模块市场形态定论：Obsidian 模式（第二轮新增）

### 6.1 为什么不是"AI 现场生成"

针对"代码门槛低了，为什么不直接让 AI 现场写模块"的质疑，用户的反驳：

> "token不要钱吗，重复造轮子不累吗？？审美和灵感依然是稀缺的，至少在现在这个2026年8月的节点，那么多vibe coding的人为什么还是很多人弄的很烂"

结论：生成成本趋近于零 ≠ 好东西的成本趋近于零。**市场卖的不是代码，是"已经被验证过的好"**——别人踩完的坑、调完的审美、沉淀的判断力。这是市场存在的第一性依据。

### 6.2 参照系：Obsidian 社区插件

> "那肯定发模块必须开源啊，就像obsidian插件市场差不多吧"

Obsidian 模式的可迁移要点：

- **强制开源**：信任链靠代码可见，不靠平台背书
- **PR 制注册表**：作者向官方注册仓库提 PR，通过后进入市场列表，零服务器成本
- **包结构极简**：manifest + 单文件逻辑（main.js ↔ logic.js）
- **Restricted Mode（建议照抄）**：社区模块默认禁用，用户手动开启才生效——一个开关即完成"官方不为第三方负责"的产品化表达
- **已知风险**：Obsidian 审核队列曾排到数周，**策展带宽是长期瓶颈**；冷启动期 PR 制完全够用

### 6.3 与第一版参照的对照

| 参照 | 问题 | 结论 |
|---|---|---|
| Unity Asset Store | 体量过大，编辑器+生态是千人团队量级 | 作为哲学参照保留 |
| 拓竹 MakerWorld | 偏硬件/模型分发，与代码模块不完全同构 | 降级为氛围参照 |
| **Obsidian 社区插件** | 体量、形态、技术栈全面匹配 | **正式参照系** |

## 七、分层分发（第二轮澄清）

第一轮曾误以为 xcbuild 与小白路径矛盾，第二轮澄清后确认是**两条互不相干的轨道**：

| 轨道 | 产物 | 受众 | 状态 |
|---|---|---|---|
| **官方 App** | App Store 正式版 | 所有人（含小白） | **已于 4 月上架** |
| **自定义 App** | 用户自行 xcbuild 的定制版 | 技术用户/极客 | 通道存在，"一条命令的事" |

小白身份定位：给**已经在用官方 iOS App** 的用户一个体验下限，与 xcbuild 通道无交集。"我不可能帮所有人上 TestFlight"——自定义 App 天生是 DIY 通道。

未来可选优化：把 xcbuild 流程做成一键按钮或 AI 可执行的 skill，进一步降低定制门槛（但 Xcode 体积、证书重签等地板仍在，优先级后置）。

## 八、关键设计原则总结（v2 更新版）

1. **门槛前置，诚实筛选**：不提供内置 API，第一步就摆明门槛，省后期客服成本。
2. **身份分流，而非统一教程**：按用户目的（酒馆/陪伴/技术）给不同路径，而非让所有人走同一条路。
3. **对话式学习，而非说明书**：AI 当教练，通过提问（场景/格式/Do-Don't）带用户写出第一条 Prompt。
4. **游戏引擎哲学**：用 ECS（Entity + Component + Scene + Prefab）组织代码，而非按页面（Page）组织。
5. **Editor / Player 分工**：Mac = Editor（组装 + 模块市场），iOS = Player（运行 + 面向所有人），iCloud 为血管（已落地）。
6. **Obsidian 式市场**：强制开源、PR 制注册表、Restricted Mode 默认禁用、manifest 权限声明必填。市场卖的是"已验证的好"，不是代码本身。
7. **苹果生态优先**：Mac 先行（原生已有），Win 版作为 Editor 的远期第二宿主，Android 最后。
8. **⚠️ 不过度复杂（用户自定硬约束）**："打算弄得更 unity 一点…虽然也不要太复杂了"。Editor 化的每一步都要问：这是把既成事实产品化，还是在为想象中的需求建空中楼阁？前者做，后者砍。

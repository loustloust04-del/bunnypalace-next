2026-10-15 · 工位 backend-3（HEAD 406f97e63）· 只读调研，没动代码 · 三份原始报告（每条都有 文件:行号）在 docs/research-model-compat/：magpie.md / ohmypi.md / mp-current.md

0. 一页结论

  • 两家的定位不同。magpie 是 Go 写的本地网关（4 种协议互翻，有多账号故障转移），怪癖全写在代码分支里（按 host、预设、模型名正则判断，注释里带 issue 号）。oh-my-pi 的 pi-ai/pi-catalog 是客户端库，怪癖做成了约 70 个 compat 开关：建模型时按「API 默认 → baseURL 主机探测 → 按模型身份的规则 → 用户覆盖」一次算好，发请求时只读字段。
  • 我们已经学过一轮。#094 参数自适配就是照这两家做的：报错分类抄 magpie 的 refusedOptional / unfit，按模型血统剥参抄 omp 的 KDL 分类。而且我们的「学到的参数」会落盘，这点比 magpie 好（magpie 只记在内存里，重启就忘）。
  • 差距集中在四块（下面 §2 有对照表）： ① SSE 解析的底层健壮性； ② OpenAI 兼容这条路完全不解析思考字段，也不回传； ③ 错误只认 400/401/403/404，限流、额度、过载、超长、内容过滤一个都不认，也不重试； ④ 怪癖判断散在各处 host 字符串里，没有集中的兼容配置；消息记录里也不存「这条是哪个模型生成的」。
  • 最急的是 P0 三件：SSE 解析修三个坑，OpenAI 兼容路解析思考字段并在工具续轮回传，错误分类加有限重试。前两件可能现在就在丢数据或报错（是读代码推断的，要实测确认）。

1. 两家各自最值得学的骨架

magpie（网关思路）

  • 统一中间表示很薄：消息只有 user 和 assistant 两种角色，system 单独成字段，流事件统一成 11 种（start/text/think/sig/toolStart/toolArgs/stop/usage/error/…）。4 种协议各写一套解析/构建/解码/编码，N×N 的翻译降成 2N（gw/ir.go）。
  • 能透传就透传，改动按字节原地做：不重排 key，保住 prompt cache 前缀，也不会被中转站判成「请求体被篡改」。
  • 剥参记忆的四条规矩：只剥白名单里的可选字段；报错里点名了才学；重试成功才写入记忆；「值不合法」不当成「不支持这个字段」。
  • 错误分三类：欠费（冷却 30 分钟）、额度用完（读 reset 头，最长等 8 天）、短时限流（1 秒起指数退避）。上下文超长统一改写成 context_length_exceeded，只让客户端压缩上下文，不换账号重试。用 paceWords 排除「Too many tokens, please wait」这类限流措辞被误判成超长。
  • 内容过滤：在模型开始说正文之前先扣住，如果以拒答结束，就换同模型的另一个账号重发。

oh-my-pi（客户端库思路）

  • compat 在建模型时一次解析好（compat/resolve.ts），发请求的代码不做任何探测。
  • 血统规则和部署契约分开放：「DeepSeek V4 的推理档位是 low/high/max」属于 class 文件；「deepseek 官方要额外发 thinking 字段」属于 provider 文件。按模型身份（class/family/revision）匹配，不按字符串，所以中转站改过名的模型 id 也能命中。
  • 思考的签名字段存「来源字段名」（reasoning_content 或 reasoning），回放时写回同一个字段，几乎零成本。
  • transformMessages：每次发送前统一整理一遍消息序列。同模型保留签名；跨模型时把思考降级成文本（发给 Claude 用裸文本，不加 <thinking> 标签，否则会触发 reasoning_extraction 拒答）；tool id 归一并给重复的加 _dupN；缺结果的调用补「No result provided」；找不到调用的结果转成 user 文本。
  • 上下文溢出判定：约 25 条各家报错措辞的正则，再加「usage 显示输入已超过窗口」兜底。不认识的 stop reason 按正常结束处理，不报错。

4. 两家踩过的、我们迟早会撞的坑（节选）

  • 同一个字段，有的厂商必须带，有的厂商禁止带：reasoning_content DeepSeek 要求必须回传，Mistral 带了就报 422（magpie 6b89fb2）。所以只能做成按厂商开关，不能全局开。
  • 用报错的原始字节做测试样本，别自己编 JSON。magpie 修文本里的工具调用时用了自造样本，结果前后修了 4 次（LESSONS.md:27-35）。
  • 某个厂商的规则只作用于这个厂商：一个 DeepSeek 报告让所有模型的上限被压到 272K，连 Claude 1M 也被误伤（LESSONS.md:85-91）。所以测试里要写「换一家模型不受影响」。
  • 空字符串、空数组不等于字段缺失：finish_reason:""、每个 delta 都带 tool_calls:[]，下游会把它们当信号（magpie chatTidy）。
  • 思考降级成文本回传给 Claude 不要加 <thinking> 标签：会触发 reasoning_extraction 拒答或泄漏（omp 18.2.1）。我们现在历史不回传思考，所以暂时安全；做 G 时要记住。
  • [DONE] 结束但没给 finish_reason 的流要当正常结束（omp 18.0.2）。

5. 多家预设与订阅登录（追加）

原始报告：docs/research-model-compat/magpie-providers.md、ohmypi-providers.md
  • 能学，分三档。真正卡住的不是技术，是厂商条款和 App Store 审核。两家的订阅登录，除了 OpenAI 的「Sign in with ChatGPT」（SIWC）和 OpenRouter，用的全是官方 CLI / IDE 的 client_id，请求头也伪装成官方客户端。
  • magpie 自己都在退：Cursor、Grok、Devin、Kiro、Qoder、Zed、Factory 等一批订阅已从本体剥离、改成社区插件，原话是「免得 magpie 本体被封」（AGENTS.md:27-29）。Claude 订阅它已经不发 HTTP，改成拉起本机真 claude，因为 Anthropic 会按请求内容（system prompt）认出第三方流量，然后记到 Extra Usage 或者封号。
  • 结构上值得抄的有三样：
    • 预设做成数据表：omp 用「KDL 声明 + 极少代码」，加一家只加一条数据。
    • Regions：同一家的国际 / 国内 / 套餐端点放在一个预设里分段选择，切换时整组端点一起换。
    • 额度卡：会员 key 能读到 5 小时 / 周窗口的剩余额度。
    三样都是纯 HTTPS，iOS 也能做。

6. 要你拍板的

Q1 范围：plan 先只做 P0（A–D），P1 放下一轮？还是 P0 加上 E（集中 compat）一起，好让 B、C 直接写进新结构，免得写完又要搬一次？
我的推荐：P0 + E 的骨架。E 先只收现有的 host 判断，再加 B、C 需要的 3 个开关；其余开关到 P1 再补。
Q2 思考显示：OpenAI 兼容路解析出来的思考（DeepSeek / Kimi / GLM / Qwen）落库后，要不要和 Claude 的思考一样显示在「思考过程」折叠里？要不要跟着现有的「思考过程」设置（隐藏 / 摘要）走？
推荐：一样显示，跟同一个设置。
Q3 自动重试的边界：5xx / 529 / 短时 429 自动重试最多 2–3 次，界面上用小胶囊显示「重试中」，可以吗？
推荐：可以；已经开始输出之后断掉的，一律不自动重试。
Q4 实测：B / C 的结论是读代码推断的。plan 之前要不要先拿你的 DeepSeek / Kimi 卡在模拟器上实测一次工具续轮，确认现在确实会 400？
推荐：要，用测试 key 或者你指定的卡，测一轮就够了。
Q5 多家预设：第一批加档 1 里的哪些？要不要顺便把预设表改成「数据表 + Regions」结构，再加额度 / 余额卡？

Q6 订阅登录的定位：现有 ChatGPT 登录 Release 里继续保留并加风险提示，还是只留在 Debug？SIWC 要不要我先去查 OpenAI 的条款？
推荐：先查 SIWC 条款。现有登录保留，加「自担风险」提示，UA 版本号实测后再修。

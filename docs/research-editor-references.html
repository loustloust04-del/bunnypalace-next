0. 结论

一句话：参考项目（Joplin、SilverBullet）没有我们这么多 iOS 绕法，是因为它们都只有一个人管键盘、一个人管滚动、一个人当文本真相源。我们这三件事都是两个人在管：键盘由 SwiftUI 缩 frame、浮条再缩一次、WKWebView 自己还在处理；撤销栈分两本，iOS 系统手势用的是 WebKit 那本，浮条按钮用的是 CodeMirror 那本；文本由 Swift 和网页双向推。之前每一轮都在 CodeMirror 里补症状，根上的两个人打架一直没拆开。

推荐方向 A：不换编辑器，照参考项目把架构收敛对，再删掉一批绕法。实现大约 3–5 天，外加实机验证。B（换原生）不推荐：Obsidian 式实时预览要从头写 6–10 周以上，Runestone 不支持 mac，STTextView 是 GPLv3、中文输入实现可疑。

先做的事：上 1 天探针，在 sim 和 Air 上把下面 F1 / F2 / U1 三条坐实再动手。它们现在都有强证据，但都还没在 iOS 实机上测过。之前的 A0 撤回修复只在无头 Chrome harness 里验过，见 docs/plan-uiux-editor-tavern-ia.md:123。

撤回「根本不对」：根因排序

#根因证据
U1iOS 系统撤回走的不是我们的历史。摇一摇、三指左滑、三指双击、iPad 键盘撤销键都用 WebKit 的撤销栈。WebKit 只给自己做的原生编辑登记步骤：CodeMirror 放行的普通打字会登记；回车（被 interceptIOSEnter 拦下）、格式命令、列表续行、浮条撤销都不登记。手势触发后，WebKit 发 beforeinput historyUndo，CM 的 history() 拦下来改做 CM 自己的 undo（bundle codemirror.bundle.js:18930-18937），撤掉的是 CM 按 500ms 分的一组。所以系统提示的「撤销键入」和实际撤掉的内容对不上；WebKit 栈先耗尽时，会弹「没有可撤销的操作」，CM 却还有历史。CM 重绘行 DOM 时 WebKit 还可能丢步。已查证CM 代码
外部证据em #5574 实机
U2实时模式和源码模式各有一本历史，而且互相污染。源码模式里的改动以 addToHistory(false) 写进藏起来的 CM（markdown-editor.js:83-86）。切回实时模式按撤销，撤掉的是进源码之前的旧改动（CM 会把它们映射到新文本上），刚在源码模式里改的东西撤不掉。源码模式每次进入都新建 TextEditor（FileLibraryPanelView.swift:2096-2097, 2213），UITextView 的撤销栈是空的。已查证
U3外部重新载入、恢复版本、「换回」之后再撤销，会撤出半截乱改的结果。这几种操作都是不进历史的最小替换，旧的历史事件被映射到替换后的文本上再执行；替换区和旧编辑重叠时，结果是半截的。SilverBullet 的做法是把外部改动 isolateHistory("full") 单独进栈，Joplin 是换文档时清空历史。已查证机制
推断具体现象
U4撤销会让那一行「跳一下」。undo 事务带着 selection，typingRevealField 遇到带 selection 的事务就清零（markdown-editor.js:1025），实时预览、表格、frontmatter 装饰随之全部重建。被撤的行从源码态收回渲染态，行高变了，再加上 undo 自带的 scrollIntoView，看起来像「撤到别处去了」。已查证代码
推断观感
U5Swift 主动推的内容可能被网页悄悄丢掉。重新载入、恢复版本、源码模式改动不会让 revision 自增，网页上还有没回报的改动时，这些内容会被当成旧回声丢掉（markdown-editor.js:76），两边文本从此分叉。概率低，但一旦发生就很难排查。已查证

1. 我们的实现与失败史

1.1 结构

  • 网页侧：MemoryPalace/Resources/Web/markdown-editor.{html,css,js}，加上 codemirror.bundle.js（IIFE，view 6.43.1 / state 6.6.0，构建脚本在 scripts/codemirror-bundle/build.sh）。
    html, body { height:100%; overflow:hidden }，.cm-editor { height:100% }，滚动发生在 .cm-scroller 内部（markdown-editor.css:20-28, 57-61）。
    viewport 设了 maximum-scale=1, user-scalable=no。
  • Swift 侧：MarkdownWebEditorView → WebViewHost，它是 UIViewRepresentable。每次 updateUIView 都把 {type:setContent, content: 全文, revision, find, command, colors, active, restore} 按 sortedKeys 序列化，和上次的 JSON 字符串比较，不同就 evaluateJavaScript（WebViewHost.swift:186-200）。
  • 网页 → Swift：contentChanged，180ms 防抖，带全文和 revision（markdown-editor.js:26-38）。Swift 收到后写 @Binding content，整个 FileEditorSheet 重算，再回推一遍（这次是 no-op 回声）。
  • 模式切换：实时编辑器常驻在 ZStack 底下，切走时只把 opacity 设成 0（FileLibraryPanelView.swift:1954-1962）；源码模式是 SwiftUI TextEditor(text:$content)，每次切进来都新建。
  • 撤销入口：
    • 浮条和宽屏格式条：实时模式下 sendMarkdownCommand("undo")，走 token 通道，在网页里调 MPCodeMirror.undo；源码模式下找到第一响应者的 undoManager 来撤（:2604-2613）。
    • ⌘Z：交给 CM 的 keymap。
    • 摇一摇和三指手势：没有任何显式处理，由 WebKit 加上 CM 的 history() 默认的 beforeinput 处理器兜底。
  • iOS 专用绕法（都在 markdown-editor.js）：
    • setEditorContent：最小 diff 替换，加 addToHistory(false)（:75-94）
    • typingRevealField：打字时离开的行先不收起（:1011-1029）
    • keepCaretVisibleOnShrink：ResizeObserver 在编辑区变矮时把光标滚回可见区（:138-149）
    • interceptIOSEnter：在 CM 之前截 keydown，preventDefault 后派合成 Enter（:151-168, 1660）
  • 另外：ShakeMonitor（加速度计，feedbackGestureEnabled 默认开）会在摇手机时发反馈通知（FeedbackSheet.swift:342-375，ContentView.swift:600）。它和系统摇一摇撤销同时触发。编辑器本身是 sheet，反馈 sheet 叠不上去，大概率只是白截一张屏。影响低，但实机测撤回时会混进噪声。

1.3 撤回链路逐点

  1. CM history：用的是 basicSetup 默认配置，newGroupDelay=500。能并组的条件是：用户事件属于 input.type|delete 或者没有标注、时间在 500ms 内、改动相邻，并且上一组之后没有发生过选区事件（bundle :19100-19104）。IME 组字（input.type.compose）总是并进上一组，所以拼音的中间态不会单独成为一步。✅ 这部分本身没问题。
  2. 浮条撤销：点按 → Swift token → 下次 updateUIView 把全文 + command 推给网页 → 网页先跑 setEditorContent（revision 守卫，通常是 no-op），再在查找词存在时重新 applyFind，最后才执行 undo 和 view.focus()。链路是对的；只是一次点按要绕整个 SwiftUI 重算、序列化全文、evaluateJavaScript。
  3. 系统手势：见 U1。WebKit 记步的范围和 CM 不一致；CM 只在 WebKit 真发出 historyUndo 时才响应，而 WebKit 只在它自己的栈还有步时才发。
  4. Swift 回写：只要 revision 守卫成立，就不会制造额外的历史事务（✅）。但 Swift 主动推的改动没有自己的 revision，见 U5。
  5. 切模式：见 U2。切走时 flushContentChanged 会先把防抖里的字发出去，所以内容不丢（✅）；问题出在两本历史不对齐。
  6. 保存：save() 不改 content，不碰历史（✅）。
  7. 重新载入 / 恢复版本 / 换回：见 U3、U5。

1.4 回车 / 打字 / 键盘 / 滚动链路逐点

  1. 回车：interceptIOSEnter 在 keydown 阶段 preventDefault，然后派合成 Enter 走 CM keymap（continueMarkdownList 或 basicSetup 的 insertNewline），并带 scrollIntoView。CM 源码里的注释说过，在 iOS 上拦 Enter 的默认行为会让键盘大小写状态卡住。我们的 contentDOM 是 autocapitalize=off（bundle :11302-11304），所以暂时没撞上。SilverBullet 用的是更稳的做法：keydown 只 stopPropagation，到 beforeinput 阶段再拦（见 §2.2）。
  2. Backspace / Delete：仍然先让 WebKit 原生删除，CM 再补，和回车之前是同一条路，有同样的居中滚动风险（F2）。
  3. 打字：原生插入，CM 的 DOMObserver 读回来。光标在可见区外时会被 WebKit 居中滚动（F2）。
  4. 键盘弹起：
    • keyboardWillShow 触发两件事：keyboardVisible=true 让浮条插进来，SwiftUI 键盘避让缩 frame。
    • WKWebView 内部还会按键盘调整 scrollView，并可能滚 document。
    • 网页里 ResizeObserver 回调 → keepCaretVisibleOnShrink → scrollIntoView。
    • CM 计算 window 可见区时用的是 visualViewport（scrollRectIntoView，bundle :4214-4300）；visualViewport 和 frame 对不上时，CM 会调 win.scrollBy，也就是去滚 WKWebView 的 UIScrollView。
  5. 键盘收起：浮条撤掉，frame 变高，WebKit 恢复 inset。没有任何代码复位 window 的滚动偏移。WebKit bug 192564 就是键盘收起后页面停在偏移位置。
  6. 点按：选区改变 → 光标行露出源码，原先那一行收回渲染态，表格和 frontmatter 块级 widget 与源码行互换，全部在触摸手势中途同步发生（F3）。

2.1 Joplin（react-native-webview + CM6，架构和我们最像）

  • 已查证编辑器是真相源，单向同步。initialText 只在创建编辑器时注入一次。useWebViewSetup.ts:59-63 的注释原话是 avoid rebuilding the string on each content change。之后编辑器通过 Change 事件把全文报给 RN（createEditor.ts:111-122），RN 不回推。整篇替换 updateBody 只给显式操作用（CodeMirrorControl.ts:135-176），插入附件等走 insertText 在编辑器里 dispatch，会进历史。每篇笔记用 key=noteId 重建编辑器（Note.tsx:2170）。
  • 已查证撤销只有 CM 一本。顶栏撤销 / 重做按钮调用 editorRef.current.undo()（Note.tsx:454-466）。undoDepth 有变化时回报，1s 防抖，撤销后立刻回报一次（createEditor.ts:81-109）。清空历史的写法是 compartment 先 reconfigure 成 [] 再 reconfigure 回 history()（:352-361）。没有对 iOS 系统撤销手势做专门处理。
  • 已查证外部滚动。MarkdownEditor.tsx:101-105 的注释写着 For better scrolling on iOS (working scrollbar) we use external, rather than internal, scrolling。.cm-editor 不限高（theme.ts 里没有 height），整个 document 滚动，也就是 WKWebView 原生的 UIScrollView 在滚，WebView 设了 scrollEnabled={true}。键盘交给 WKWebView 原生处理：NoteEditor.tsx:105-107 的注释说 iOS 键盘打开时会自己往底部加 padding。
  • 已查证键盘弹起时只滚一次光标。点按后 1 秒窗口内，window.onresize 触发 scrollSelectionIntoView，窗口外的 resize 一律不滚（useWebViewSetup.ts:81-103）。
  • 已查证iOS 上装饰更新推迟到手势结束之后（makeInlineReplaceExtension.ts:46-55，注释原话 To prevent unnecessary scroll on iOS…）。按下时记住旧选区，手势进行期间仍按旧选区算装饰，mouseup 之后用 rAF 再刷新。装饰只做单行 inline replace，不跨行。
  • 已查证hideKeyboardAccessoryView，WebView 背景透明防白闪，iOS 上 decelerationRate='normal'（ExtendedWebView/index.tsx:113-147）。

2.2 SilverBullet（CM6 PWA，iOS 26 实战）

  • 已查证iOS 回车在 beforeinput 阶段接管（client/codemirror/editing/ios_enter.ts:13-111）：
    • keydown 只 stopPropagation，不 preventDefault，iOS 仍会发 beforeinput，自动大写状态也保持正确。
    • beforeinput 遇到 insertParagraph / insertLineBreak 时 preventDefault。
    • 先 syncSelectionFromDOM()，以原生光标为准。
    • 再 runScopeHandlers 跑一次 keymap。
    • 500ms 内没等到 beforeinput 就兜底执行一次，之后 1s 内再来的换行一律吞掉。
    注释写的原因：CM 的「原生先插、再补合成键」做法会在超时后插两次换行，点开键盘那一下还可能让选区不同步。
  • 已查证键盘可见区自己管（client/lib/keyboard_viewport.ts）：
    • 注释（:12-14）：WebKit only shrinks the visual viewport, and on iOS 26 also scrolls the document (despite overflow: hidden) to reveal the caret。
    • 每次 visualViewport 事件都先 scrollTo(0,0)，把根容器 position:fixed 钉在 --sb-viewport-top/height 上。
    • 每个事件之后再补一帧 rAF，因为 WebKit 要到下一帧才定下最终 viewport。
    • 键盘在场时 scrollIntoView(head,{y:"nearest",yMargin:24})（keyboard_bar.tsx:131-142）。
  • 已查证滚动方式和我们一样是内滚：html,body{height:100%;overflow:hidden}，.cm-editor{height:100%}（main.scss:19-27，editor.scss:33-35）。viewport meta 带 interactive-widget=resizes-content。我们这套 CSS 是对的，缺的是 iOS 26 滚 document 之后的复位。
  • 已查证外部改动：先三方合并算出最小 ChangeSet，再带 isolateHistory("full") 进撤销栈，单独成组，可以撤（content_manager.ts:796-806，external_merge.ts:27-58）。换页时用 setState 重建（历史随之清空）。启动后先清一次历史（client.ts:441-446）。
  • 已查证防跳：
    • 点击（select.pointer）时沿用旧装饰，组字期间只 map 不重算。
    • 块 widget 带 estimatedHeight 并缓存实测高度。注释说不估高，滚动会跳几千 px（table.ts:39-47）。
    • 多行块源码的隐藏方式：放 widget 的那行 replace，其余行加 display:none 的行 class，避免多行 replace 变成原子范围（util.ts:238-281）。
    • WebKit 没有 requestIdleCallback，补一个 16ms 的 polyfill，防止后台解析退化成 500ms 停顿、期间闪出源码（index.html:38-51）。
  • 已查证CHANGELOG 里记的 iOS / WebKit 修复：
    • 列表里回车多插一行（:33）
    • 粘贴后第一个键插错位置（:164）
    • 移动端任务行光标跳（:317）
    没有 iOS 撤销手势相关的记录。

2.3 原生对照：Runestone / STTextView

RunestoneSTTextView
平台只支持 iOS 14+；Catalyst「未完成」，没有 macOS（Package.swift:9，README:51）macOS 14 / iOS 16，TextKit 2；AppKit 和 UIKit 两套独立实现，UIKit 端功能明显更少

3. 已知 issue / 官方动向

  • 外部证据cybersemics/em #5574（2026-09 合并，iPhone 实机）的结论：
    • Safari 把三指撤销手势作为可取消的 beforeinput historyUndo 发出，只在 WebKit 自己的历史里还有步时才发。
    • WebKit 只登记它自己做的编辑，所以 app 用程序重绘 editable 的那些改动，WebKit 一步也不记。
    • preventDefault 不会阻止 WebKit 推进历史位置，每次手势消耗一步，耗尽后 iOS 弹「没有可撤销的操作」，而 app 其实还有历史。
    • 他们的修法是每次手势之后「回放再反向」一次，把 WebKit 的历史位置回收回来，并加一个锚定步。修法相当复杂。前一个 PR #4723 是把手势路由到 app 自己的撤销。
    这和 U1 完全对上。
  • 外部证据W3C UndoManager 会议纪要（2019）：WebKit 的 whsieh 说 CodeMirror 这种自己管 DOM 的 contenteditable 和系统 Edit > Undo 配合不好；系统级撤销（菜单、三指）不会通知网页内容。
  • 已查证CodeMirror view 的 CHANGELOG（codemirror/view）：
    • 6.40.0：Shift-Enter / Backspace / Delete 在 iOS 上丢 shift 修饰键
    • 6.39.17：drawSelection 在 iOS 上自绘选择手柄
    • 6.38.5：Safari 26 聚焦时不当滚动
    • 6.38.6：Safari 26 残留旧选区碎片
    我们打包的是 view 6.43.1，上游这些修复都已包含，再升级 CM 也解决不了本文这些问题。
  • 外部证据codemirror/dev #482「iOS sometimes enter gets stuck」：报告者怀疑和回车时的自动大写 hack 有关；Marijn 的回应是让 iOS 上的 Enter / Backspace 处理更健壮。说明 iOS 的回车本来就是 CM 的高危区。
  • 外部证据Capacitor Keyboard 插件 Keyboard.m：
    • [nc removeObserver:self.webView name:UIKeyboardWillHideNotification …] / …DidChangeFrame…，移除 WKWebView 自己的键盘处理
    • scrollView.scrollEnabled = NO
    • setContentInset:UIEdgeInsetsZero
    • scrollViewDidScroll 里 setContentOffset:CGPointZero
    这是业界在「宿主自己缩 WebView」时关掉 WebKit 那份键盘处理的标准做法。
  • 外部证据WebKit bug 192564：键盘收起后 web view 停在偏移位置，Cordova、react-native-webview、Capacitor 都受影响。

5. 推荐方向

A（推荐）：保留 CM6，照参考项目收敛架构 —— 约 3–5 天实现，另加实机验证

A0 探针（1 天，先做）：在 sim 和 Air 上记录以下数据，坐实 F1 / F2 / U1。

  • window.scrollY、visualViewport.{height,offsetTop}、scrollDOM.{scrollTop,clientHeight}
  • Swift 侧 webView.scrollView.{contentOffset,contentInset,adjustedContentInset}、frame 高度
  • 所有 beforeinput.inputType（重点看 historyUndo / historyRedo）、CM 的 undoDepth

脚本：打字到屏幕底 → 回车 → Backspace 合并行 → 点按表格 → 弹收键盘 → 摇一摇 / 三指撤销。

  1. 键盘只留一个人管（解决 F1 / F5）。推荐 A1-b：照 SB + Capacitor：
    • 保留内滚和 SwiftUI 缩 frame。
    • WKWebView 设 scrollView.isScrollEnabled=false、contentInsetAdjustmentBehavior=.never，并用 scrollView delegate 把 contentOffset 钉在 0。
    • 网页侧在 visualViewport resize / scroll 时，如果 scrollY≠0，就 scrollTo(0,0)，并补一帧 rAF。
    • 浮条插入不再单独引起一次缩放：改成固定占位，或者浮条和键盘同一帧出现。
    • 删掉 keepCaretVisibleOnShrink，换成 Joplin 式「点按后 1s 内的 resize 才滚一次光标」。
    备选 A1-a：照 Joplin：改 document 外滚，WebView .ignoresSafeArea(.keyboard) 不缩，交给 WKWebView 原生 inset。手感更原生，但改动大，原生的露光标逻辑会不会居中还要实测 推断。
  2. 回车、退格改在 beforeinput 阶段接管（解决 F2）：照抄 SB 的 ios_enter.ts 思路，替换现在的 interceptIOSEnter；Backspace 合并行（deleteContentBackward 跨行时）同样处理。普通字符仍然原生插入，但修好 F1 之后光标不会再落在可见区外。
  3. 装饰防跳（解决 F3 / F4 / U4）：
    • 指针选区变化推迟到触摸结束（Joplin 做法），或者 select.pointer 时沿用旧装饰（SB 做法）。
    • 表格、frontmatter widget 加 estimatedHeight 和实测高度缓存。
    • undo / redo 事务不清空 typingRevealField，等下一次真正的光标移动再收起。
  4. 文本改成单向同步（解决 U5 / F6）：
    • JS 是真相源，Swift 只接收 contentChanged。
    • setContent 只在显式操作时发：打开、重新载入、恢复、换回、从源码模式切回。每次带 Swift 自增的 nativeRevision，网页无条件应用。
    • 普通的 body 重算不再推全文：payload 去掉 content，单独发。
  5. 一本撤销账（解决 U2 / U3）：
    • 外部写入改成 isolateHistory("full") 进栈（可以撤回到恢复之前），或者干脆清空历史（Joplin 的 compartment 写法）。
    • 源码模式的改动在切回实时模式时，作为一步写进 CM 历史，切换期间不再每次按键都推。
    • 源码模式内部仍然用 UITextView 自己的撤销，这一点在 UI 上说清楚。
  6. 系统撤销手势（解决 U1）。三档，需要粟粟拍板：
    • (i) 最小：浮条撤销是唯一入口，实时模式下关掉摇一摇撤销（applicationSupportsShakeToEdit=false 是全 App 开关，会影响所有文本框，要她点头）。三指手势仍会出现不准的提示。
    • (ii) 推荐试：沿用 WKWebViewNoAccessory.swift 的动态子类手法，覆写 WKContentView 的 undoManager，返回一个代理：canUndo/canRedo 取 CM 回报的 historyState，undo()/redo() 发命令给 CM。这样摇一摇、三指、iPad 撤销键全都走 CM 一本账。UIKit 手势是否真的通过 responder 的 undoManager 走、WebKit 内部会不会绕开，必须实机验证 推断。
    • (iii) em 的「回收历史位置」方案：有实机证据能用，但复杂、很脆，不推荐。

能删的绕法（A 做完后）：

  • keepCaretVisibleOnShrink：由 1 取代
  • interceptIOSEnter：由 2 的 beforeinput 版取代
  • 每次 body 重算推全文、靠 revision 守卫的整套回声：由 4 取代

setEditorContent 的最小 diff 保留，但只用于显式外部写入，并且改成进栈。typingRevealField 保留，它是交互设计，不是绕法。

风险：

  • WKWebView 的键盘和滚动行为属于 WebKit 私有行为，iOS 小版本之间会变，需要固定一套实机回归脚本。
  • (ii) 覆写 undoManager 用的是 runtime 手法，和现在去掉键盘浮条用的是同一类，已有先例，但同样依赖私有类名前缀 WKContent。

B：换原生编辑器 —— 不推荐

  • 收益：撤销天然是一本 UndoManager，系统手势自动对上；没有 WebKit 的滚动行为。
  • 成本：
    • Runestone 只有 iOS，mac 还得另做一套，而且不能隐藏字符、没有块级 widget，Obsidian 式实时预览要 fork 引擎核心，6–10 周以上 推断。
    • STTextView 跨端，但 GPLv3（闭源要买商业授权），UIKit 端功能少，中文 marked text 实现可疑，4–8 周，外加 TextKit 2 的坑 推断。
    • 现有的 frontmatter 卡、表格、wiki link、checkbox、查找替换、版本历史接口全部要重写。
  • 风险：中文输入法、长文性能、mac 和 iOS 两套行为要重新踩一遍坑。只有 A 做完、实机仍然不可接受时，才值得重新评估。

C：折中 —— iOS 上实时模式降级

iOS 上默认用源码模式（UITextView，原生撤销和滚动，可以加轻量语法着色），再加一个预览页；实时预览只在 mac / iPad 宽屏上开。工作量 1–2 天。代价是 iPhone 上丢掉所见即所得，属于产品取舍，要粟粟决定。可以作为 A 进行期间的临时止血。

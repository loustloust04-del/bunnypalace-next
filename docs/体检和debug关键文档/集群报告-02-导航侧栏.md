## D1 架构分层

**1. SidebarView 是 God View：搜索编排、分页 fetch、predicate 工厂、导出、标签 CRUD 全压在一个 2676 行的 View 里**
- 文件: SidebarView.swift:27-1820
- 严重度: P1
- 现状: body 本体约 95-688 行（~590 行）；View 内含 `fetchPage/normalPredicate/trashPredicate/triggerSearch/exportConversation/deleteTag/scopeForCurrentTab` 等十几个数据层方法，直接持 `modelContext` 做 CRUD（如 L418 `modelContext.insert(item)`、L1069 `modelContext.delete(tag)`、L1070 `try? modelContext.save()`）。
- 风险: 列表数据源逻辑无法单测；搜索状态机（9 个 @State 结果数组/标志位）和 UI 强耦合，后续改任何一个搜索类型都要在这个文件里动刀。这是本集群最大的一坨技术债。

**2. View 层直接配置网络客户端（CC Bridge 接线写在 ContentView.onAppear）**
- 文件: ContentView.swift:287-302
- 严重度: P2
- 现状: `CCBridgeWebSocketClient.shared.connect(urls:token:)` + `onProactiveMessage` / `onEditMessage` 回调赋值都在 View 的 `.onAppear` 里，还自己读 UserDefaults + Keychain。
- 风险: 连接生命周期绑在 View 出现时机上；onAppear 若重入会重复 connect（依赖 client 内部幂等）；这类 app 级服务应在 App/AppDelegate 层初始化。

**3. 依赖注入三种风格混用：@Environment 可选 + `?? ThemeManager.shared` 回退 + 纯单例**
- 文件: ContentView.swift:21,137,377,473（`themeManager ?? ThemeManager.shared` 出现 4 处）；DashboardView.swift:7（`@State private var dash = DashboardManager.shared`）；ContentView.swift:297,417,428（`CCBridgeWebSocketClient.shared`）
- 严重度: P2
- 现状: 所有 manager 都注成 optional `@Environment`，然后散落各处做 nil 回退；Dashboard 直接抓单例放 @State。
- 风险: 同一个 manager 可能两条获取路径（环境注入的实例 vs .shared），预览/测试里行为分叉；nil 回退掩盖"忘了注入"的 bug（如 SidebarView 多处 `profileManager?.currentProfile.id ?? ""` 拿到空串后 predicate 静默匹配不到任何数据，表现为"列表空了"而不是报错）。

**4. View 直接改 @Model 字段，且和走 viewModel 的路径并存**
- 文件: ContentView.swift:609 / 678-679 / 723-725；SidebarView.swift:363-365 / 399 / 484
- 严重度: P2
- 现状: ContentView 的 unpin 直接写 `target.isPinned = false; target.pinnedAt = nil`（L678-679），而 BranchMapSheet 同样的操作走 `viewModel.togglePin(n)`（BranchMapSheet.swift:114）；重命名走 `conv.title = trimmed` + `markConversationDirty()`，收藏 toggle（ContentView.swift:609、SidebarView.swift:399）却不调任何 dirty/refresh。
- 风险: 同一业务两条写路径，收藏 toggle 后侧栏"收藏" tab 列表不会刷新（refreshList 不被触发），数据与 UI 短暂不一致。

**5. macOS 双布局（normalLayout / fullscreenLayout）整段复制**
- 文件: ContentView.swift:795-848 vs 851-905
- 严重度: P2
- 现状: SidebarView 构造、CardFlowView/EmptyStateView 切换、PanelDivider + RightPanelView 整块（828-837 与 884-893 逐字相同）在两个布局里各写一遍。
- 风险: 已知 DRY 违反；右栏宽度逻辑改一处漏一处的概率很高。NavigationSplitView 本身用法正确（带 columnWidth），全屏换 HSplitView 是有意的，但共享子块应抽出。

## D2 SwiftData

**1. 【实质 bug】标签 tab 分页坏死：fetchPage 忽略 offset，且每次全量 fetch 非删除会话**
- 文件: SidebarView.swift:1474-1495（配合 loadMore L1435-1438、最后一行 onAppear L451-454）
- 严重度: P1
- 现状:
  ```swift
  if let tagId = selectedTagId {
      ... // fetch 该 tag 全部 FavoriteItem
      if let allConvs = try? modelContext.fetch(convDescriptor) {   // 无 fetchLimit，全量非删除会话
          let filtered = allConvs.filter { convIds.contains($0.id) }
          totalCount = filtered.count
          conversations = Array(filtered.prefix(pageSize))          // offset 参数被无视
      }
  ```
- 风险: 标签下超过 100 条会话时永远只显示前 100 条，footer 却显示"显示 100 / N"；滚到底触发 `loadMore() → fetchPage(offset: 100)` 仍然重置回前 100 条，等于每次滚到底白做一次"全量 Conversation fetch + 内存过滤"。功能性 bug + 性能债二合一。

**2. 每个键击触发两次同步 SQLite 查询（无防抖）**
- 文件: SidebarView.swift:668-671 → fetchPage L1500/1507（fetchCount + fetch），predicate 含 `title.localizedStandardContains`
- 严重度: P2
- 现状: `.onChange(of: searchText) { ... refreshList() }`，每个字符在主线程同步跑 count + 分页 fetch，contains 谓词无索引可用。
- 风险: 千级会话量下打字会有可感卡顿；建议 debounce（搜索本体已有 ➡️ 显式触发，列表过滤这条没有）。

**3. fetchConversationTitleMap 每次全量 fetch 整张 Conversation 表只为取标题**
- 文件: SidebarView.swift:1095-1105（被 fetchFavoritedNodes L1120、fetchDeletedNodes L1139 各调一次）
- 严重度: P2
- 现状: `FetchDescriptor<Conversation>(predicate: profileId)` 无 fetchLimit、无 propertiesToFetch，物化全部模型对象建 [id: title] map。
- 风险: 收藏/回收站 tab 每次 refreshList（含每个键击、sheet 关闭、sidebarRefreshTrigger）都全量拉一遍；应改 `propertiesToFetch: [\.id, \.title]` 或按 nodes 涉及的 conversationId 收窄。

**4. EmptyStateView 用 @Query 拉全部会话只为判断 isEmpty**
- 文件: ContentView.swift:1142-1148
- 严重度: P2
- 现状: `@Query(filter: profileId predicate)` 无 fetchLimit，body 只用 `conversations.isEmpty`。
- 风险: 无选中会话时（macOS 空态 / iOS 空态）整个 profile 的会话被 query 物化；`fetchLimit = 1` 即可。

**5. 加标签可插入重复 FavoriteItem，无去重**
- 文件: SidebarView.swift:411-419
- 严重度: P2
- 现状: contextMenu "加标签" 直接 `modelContext.insert(FavoriteItem(...))`，不检查该 (conversationId, tagId) 是否已存在。
- 风险: 重复点击同一标签 → DB 里堆重复行；显示层用 Set 去重所以看不出来，但数据持续脏化，删 tag 时才一起清。

**禁令核查结果：本集群未发现无条件 `FetchDescriptor<MessageNode>()` 全量 fetch。** SidebarView.swift:1109/1128 两处 MessageNode fetch 均带 `profileId == pid` + isFavorite/isDeleted 谓词；ContentView/BranchMapSheet 的 Conversation/MessageNode fetch（ContentView.swift:461、SidebarView.swift:1366 等）也全部带 profileId。ConversationViewModel.navigateToSearchResult 按 conversationId+profileId 收窄，合规。唯一注意点：fetchFavoritedNodes/fetchDeletedNodes 虽然带谓词但无 fetchLimit——收藏/已删节点数量理论上无上界，建议加 limit 或分页（P2 顺带）。

## D3 并发安全

**1. ImportView 的 Task.detached 无句柄、不可取消、无完成回收**
- 文件: ImportView.swift:678-696
- 严重度: P2
- 现状: 两个分支各自 `Task.detached(priority: .userInitiated)` 跑导入，句柄丢弃。iOS 用 `interactiveDismissDisabled(isImporting)`（L238）挡了下滑关闭，macOS 侧没有任何 dismiss 防护（取消按钮 disabled 是唯一约束）。
- 风险: 导入中无法取消；用户中途切 profile（profileId 已快照进 importer，数据不会串楼层，这点没问题）后导入仍写入旧楼层但 UI 已换层，完成状态无人消费。

**2. ImportHistoryView 撤回用裸 GCD + 跨线程读 @State self**
- 文件: ImportHistoryView.swift:94-146
- 严重度: P2
- 现状: `DispatchQueue.global().async` 里捕获 struct self，循环中每条 change 都 `DispatchQueue.main.async { deleteProgress = ... }`（L125-127）。
- 风险: 每条 change 派一个 main block，几千条时 main queue 被进度更新刷屏；与项目其它地方的 Task/actor 风格不一致。功能上 bgContext 独立、状态写回主线程，无数据竞争。

**3. 搜索任务取消窗口期可能写入过期结果**
- 文件: SidebarView.swift:1223-1299
- 严重度: P2
- 现状: `guard !Task.isCancelled else { return }` 在 await 之后、`MainActor.run` 之前检查。若用户在这两步之间触发新搜索（cancel + 新 task 启动），旧 task 的 `MainActor.run` 仍会执行，旧结果覆盖新结果（取决于调度顺序）。
- 风险: 低概率"结果闪回旧关键词"；把 isCancelled 检查移进 `MainActor.run` 内即可闭环。总体而言这里的取消纪律（triggerSearch L1213、clearSearch L1194 都 cancel）是做得好的。

**4. WindowFullscreenObserver.updateNSView 在视图更新期内同步写 @Binding**
- 文件: ContentView.swift:999-1010 → attach L1033-1034
- 严重度: P2
- 现状: `updateNSView` 调 `attach`，attach 末尾同步执行 `onStateChange(...)` / `onWidthChange(...)`，即在 SwiftUI update pass 中写 `isFullscreen/windowWidth` 绑定。
- 风险: 典型 "Modifying state during view update, this will cause undefined behavior" 触发点；makeNSView 走了 `DispatchQueue.main.async`（L984）说明作者意识到这个问题，但 updateNSView 路径漏了同样的处理。

## D4 内存/性能

**1. ContentView.body 每次重算都跑全树 DFS（branchOffMainCount）**
- 文件: ContentView.swift:760-762（在 iOSChatTopBar L581 消费）
- 严重度: P2
- 现状: `private var branchOffMainCount: Int { viewModel.collectAllBranches().count }`，collectAllBranches 是全树 DFS + 每条分支算 branchLength。
- 风险: iOS 上 ContentView.body 重算（换页、流式边界、键盘等）都会对当前会话做一次 O(N) 遍历；几千节点的大会话上是无谓的重复计算。可缓存到 viewModel 并在 tree 重建时失效。

**2. BranchMapSheet 渲染路径上的重复快照与平方级扫描**
- 文件: BranchMapSheet.swift:24-26（currentPathIds 每次调用重建 Set）、151（nodeView 内每个节点调一次 `viewModel.branchMapSnapshot()`）、265（drawConnections 再调一次）、297-305（isEdgeOnPath 对每条边做两次 `visibleNodes.first(where:)` 线性扫 ×2 种 path）
- 严重度: P2
- 现状: 每帧渲染 = N 个 nodeView × (新建 snapshot + 新建 currentPath Set) + E 条边 × 4 次 O(V) 线性查找；另外 computeLayout（L65）在 GeometryReader 闭包里，任何 body 重算都整树重建+重排版。
- 风险: 折叠机制让可见节点数有界，小树无感；分支多的大会话打开/点选会明显掉帧。把 snapshot/Set/nodeId→VisibleNode 字典提为 layout 一次性产物即可。

**3. ImportRecordRow 每次 body 新建 DateFormatter**
- 文件: ImportHistoryView.swift:165-169
- 严重度: P2
- 现状: `private var dateString: String { let formatter = DateFormatter() ... }`，DateFormatter 构造是出了名的贵。
- 风险: 记录条数少所以实际影响小，但同文件集群里 ContentMatchRow（SidebarView.swift:2255-2259）已示范了 static formatter 正确写法，属低垂果实。

**4. DashboardView 的 repeatForever 抖动动画 onAppear 即启动、永不停止**
- 文件: DashboardView.swift:62-64（消费在 L122）
- 严重度: P2
- 现状: `.onAppear { withAnimation(.easeInOut(...).repeatForever(...)) { wobble = true } }`，与 editing 无关地常驻。
- 风险: 非编辑态 rotation 恒为 0，CoreAnimation 大概率优化掉，但这个动画事务挂在页面整个生命周期；绑定到 `editing` 的 onChange 上更干净也更省。

**5. `.transaction { tx.animation = nil }` 全局杀动画，使子树内多处 withAnimation 成为死意图**
- 文件: ContentView.swift:284-286
- 严重度: P2
- 现状: 挂在主 ZStack 链上的无条件 transaction 覆写，会拦截流经该子树的全部隐式/withAnimation 动画；而同文件 L267/275/910 和 SidebarView 内大量 `withAnimation(...)` 包裹的状态改动落点都在这个子树内。
- 风险: 这些 withAnimation 实际不生效（或仅对子树外生效），代码表达的意图与运行行为不一致；后人调动画会在错误的地方排查。如果"全局无动画"是有意的，那些 withAnimation 包装就是该清的死代码。

ForEach identity 总体健康：`ForEach(conversations, id: \.id)`、`ForEach(favoritedNodes, id: \.node.id)`、工具/widget 用 Identifiable，未见用 index 当 identity 的可变列表（DashboardView L23 的 `id: \.offset` 作用于"行"而非 widget 本身，行内 ForEach(row) 用的是 Identifiable，可接受）。未发现强引用循环：闭包捕获多为 weak viewModel / weak window，WindowFullscreenObserver.Coordinator deinit 移除 observer（L1018-1020）正确。

## D5 错误处理

**1. ImportView.startImport 三连吞错：security scope 失败静默 return、copy 失败静默继续**
- 文件: ImportView.swift:662-668
- 严重度: P1
- 现状:
  ```swift
  guard url.startAccessingSecurityScopedResource() else { return }   // 无任何提示
  try? FileManager.default.removeItem(at: tempURL)
  try? FileManager.default.copyItem(at: url, to: tempURL)            // 失败则后续导入读不到文件
  ```
- 风险: 这是导入的主入口。沙盒授权失败时用户点了文件却毫无反应；copy 失败（磁盘满/iCloud 未下载）后 importer 拿到不存在的 tempURL，报出来的会是与真因无关的解析错误。文件选择器错误也只 `print`（L212）。

**2. ImportHistoryView 撤回中途失败：静默中止 + 留下半撤回状态**
- 文件: ImportHistoryView.swift:112-128
- 严重度: P1
- 现状: 循环里 `catch { DispatchQueue.main.async { isDeleting = false }; return }`——前面每 25 条已 `try bgContext.save()`，失败时既不回滚、不删 record、也不给用户任何提示，进度条直接消失。
- 风险: 数据处于"撤回了一半"的中间态，ImportRecord 还在，用户再点撤回会对已恢复的 change 重复 restore。至少要弹错误 + 标记 record 为部分撤回。

**3. 导出 Markdown 写文件失败静默**
- 文件: SidebarView.swift:731（`try? markdown.write(to: url, ...)`）
- 严重度: P2
- 现状: NSSavePanel 确认后写盘，失败无任何反馈。
- 风险: 用户以为导出成功实际没有文件；这是用户数据出口，建议至少 NSAlert。

**4. `try? modelContext.fetch/save` 弥漫式吞错（约 20 处）**
- 文件: SidebarView.swift:1066/1070/1100/1115/1134/1454/1461/1482/1487/1500/1507/1738/1783/2644 等；ContentView.swift:462
- 严重度: P2
- 现状: 所有 fetch 失败一律静默回退为空列表/空 map。
- 风险: SwiftData store 出问题时表现为"列表空了/搜不到"，无日志可循。鉴于本项目有"诡异 bug 先加探针"的教训，至少失败分支补一条 log。

**5. 推送跳转静默丢弃且不可重试**
- 文件: ContentView.swift:457-464
- 严重度: P2
- 现状: `consumePendingPushTarget` 先 `removeObject(forKey:)` 再校验 conv 是否存在/currentNodeId 非空，任一失败直接 return。
- 风险: 冷启动时 conv 尚未就绪（0.6s 魔数延迟 L309 赌的就是这个），赌输了 pending key 已被删，点推送进 app 落在无关页面且无任何提示。

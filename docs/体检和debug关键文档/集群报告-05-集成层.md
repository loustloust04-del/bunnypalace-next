## D3 并发安全（重点）

### [P1] MCPClient 请求超时分支挂死：continuation 永不 resume，TaskGroup 等不到子任务退出
**文件**: `Services/MCP/MCPClient.swift:99-122`
**现状**:
```swift
return try await withThrowingTaskGroup(of: [String: Any].self) { group in
    group.addTask { @MainActor in
        try await withCheckedThrowingContinuation { continuation in
            self.pending[id] = continuation
            ...
        }
    }
    group.addTask {
        try await Task.sleep(nanoseconds: UInt64(self.requestTimeout * 1_000_000_000))
        throw MCPError.requestTimeout(method)
    }
    guard let result = try await group.next() else { ... }
    group.cancelAll()
    pending.removeValue(forKey: id)
    return result
}
```
**风险解释**: 超时子任务先抛出时，`group.next()` rethrow，body 以 throw 退出 → TaskGroup 隐式 cancel 并**等待**剩余子任务结束。但 cancel 不会 resume 卡在 `withCheckedThrowingContinuation` 的子任务（pending 里的 continuation 只有 server 回包 / handleClose / disconnect 才 resume）。结果：server 不回包且连接不断时，`sendRequest` 永远不返回——超时机制名存实亡。连锁影响：`heartbeat()`（MCPProvider.swift:322-332）的 `listTools()` 挂死 → 心跳 Task 永久卡住、`reconnectWithBackoff` 永不触发；`callToolText` 挂死 → 工具调用回合卡死整个聊天回合。另外超时路径不执行 `pending.removeValue(forKey: id)`，continuation 泄漏。
（总报告升级为 P0-3。）

### [P1] MCPSSETransport.connect 的 endpoint 等待是同一个挂死模式
**文件**: `Services/MCP/MCPSSETransport.swift:81-93`
**风险解释**: SSE 连上（HTTP 200）但 server 一直不发 `endpoint` 事件时，10s 超时抛出后 group 仍要等 continuation 子任务 → `connect()` 永远挂起 → `MCPProvider.connect` 卡在 `connecting` 状态不落 error。这正是"SSE server 连不上且无报错"的另一种表现形态。附带：`self?.endpointContinuation = continuation` 若 self 已释放，continuation 直接泄漏。

### [P2] MCPSSETransport 全部可变状态跨线程无同步
**文件**: `Services/MCP/MCPSSETransport.swift:8-12, 97, 116-121, 125-128, 160-168`
**现状**: `messageEndpoint` 在 streamTask 的 processEvent 里写（:126），在调用方任意线程的 send() 里读（:97）；`closed` 在 close()（任意线程）写、stream 循环里读（:61）；`endpointContinuation` 在 group 子任务写、streamTask 的 finishEndpointIfNeeded 读改——两线程同时过 guard 会 double-resume crash。
**风险解释**: 类无 actor/锁保护，全靠时序巧合。TSan 必报；极端时序下是 checked continuation double-resume 崩溃。

### [P2] CCBridgeWebSocketClient 的 task/session/urls/currentIndex/reconnectDelay 跨线程读写
**文件**: `Services/CCBridgeWebSocketClient.swift:429-431, 437-439, 253, 597-608`
**风险解释**: 设计上用「只认当前 task」的 identity 比较防 ghost reconnect，思路对，但属性本身是普通 var，非原子。实践中多为良性竞争，但属于未定义行为，TSan 会报；handlersQueue 已存在，这些状态没收进去是一致性缺口。

### [P2] 同一连接断开可触发两次 handleDisconnect → 退避一次翻两倍
**文件**: `Services/CCBridgeWebSocketClient.swift:441-442, 681-691`
**风险解释**: receiveLoop 的 .failure 与同一 task 的 didCloseWith 委托回调都调 handleDisconnect。两次 scheduleReconnect：第二次 invalidate 第一次的 timer，不会双连接，但 reconnectDelay 一次断连 1→2→4 跳两档。轻微。

### [P2] MCPProvider.connect 的 check-then-act 跨越 await 悬挂点，并发 connect 产生双 client
**文件**: `Services/MCP/MCPProvider.swift:139-156`
**风险解释**: @MainActor 保证不并行，但两个 connect 在 `try await client.connect` 悬挂点交错：都过了 `clients[serverId] == nil` 检查 → 各建一个 transport+client，后写入者覆盖前者，前者的 SSE 流无人 close。缺 `statuses == .connecting` 的入口挡板。

### [P2] CCBridgeProvider.cancel() 不注销 reply handler，取消后晚到的回复仍会触发 onComplete
**文件**: `Services/ChatService.swift:1067-1078`（结合 :989-996）
**风险解释**: registerReplyHandler 注册的闭包留在 replyHandlers 字典里。用户取消后 CC 的 reply 到达 → handler 命中 → onComplete(replyText, nil) 照常回填 UI。如果"取消后仍落消息"是有意为之，至少 streamingContent 状态机与取消语义打架；handler 持有的上下文也滞留。

### [P2] SpeechService 的 delegate 回调线程未保证
**文件**: `Services/SpeechService.swift:41-47`
**风险解释**: didFinish/didCancel 直接写 activeNodeId，UI 在 main 读。AVSpeechSynthesizer 的 delegate 回调线程 Apple 未承诺 main。低概率撕裂读。

其余：URLSession delegate（didOpen/didClose）全部先 hop 到 main 再碰 @Observable 状态 ✓；ping/reconnect Timer 闭包均 `[weak self]` ✓；handlersQueue 对 replyHandlers/terminal handlers/seenReplyIds 的串行保护完整 ✓；receiveLoop 用 `self.task === currentTask` 防 ghost reconnect 的写法正确 ✓。

## D4 内存

### [P2] MCP 连接失败不 close transport，SSE 流 Task 强持 transport 悬挂
**文件**: `Services/MCP/MCPProvider.swift:157-162` + `MCPSSETransport.swift:34-35`
**风险解释**: connect 的 catch 分支只 removeValue，从不调 transport.close()。而 streamTask 里 `guard let self else { return }` 把 [weak self] 升级为整个 for-await 循环期间的强引用。initialize 超时或 listTools 失败后，已建立的 SSE 长连接无人关闭；reconnectWithBackoff 3 次重试 = 最多 3 条悬挂连接 + 3 个活 Task。对常开 app 是缓慢的连接/内存泄漏。

### [P2] listHandlers / spawnHandlers 无超时，hub 不回包则 completion 永久积压
**文件**: `Services/CCBridgeWebSocketClient.swift:92-94, 290-302, 400-413`
**风险解释**: send 成功但 hub 没回（hub 重启、协议不匹配）→ handler 连同其捕获的 UI 闭包永远留在字典里，UI 侧 spinner 永转。量级小但无界累积 + 无用户反馈，属于双重缺陷（D4+D5）。

### [P2] FileLibraryTools/Store 在主线程做全量文件 IO
**文件**: `Services/FileLibraryStore.swift:197-208` + 调用点 `ViewModels/ConversationViewModel.swift:1909`
**风险解释**: search() 对库内每个文件 read() 全文；executor 在 @MainActor 的工具循环里同步执行。文件库大了之后 fs_search/fs_read 直接卡 UI。当前库小，先记账。

正面确认：seenReplyIds 按条数 prune（600）+ 持久化，有界且与 hub MAX_REPLY_LOG 的余量关系写明 ✓；reconnect/ping Timer 均 weak、startTask 前 invalidateAndCancel 旧 session ✓；未发现闭包 retain cycle。

## D5 错误处理

### [P2] legacy 迁移全部失败时仍标记"迁移完成"，永不重试
**文件**: `Services/FileLibraryStore.swift:353-355`
**现状**: `if !failed || !copiedAny { UserDefaults.standard.set(true, forKey: key) }`
**风险解释**: 全部文件拷贝失败时 `failed=true, copiedAny=false` → `!copiedAny` 为 true → 标记 done。意图显然是"部分失败下次重试"，但布尔条件把"全失败"也放过了。用户从此看到空文件库且无任何提示。正确条件应是 `!failed`。

### [P2] CharacterCardManager.createFloor 的 `try? context.save()` 吞错
**文件**: `Models/CharacterCard.swift:182`
**风险解释**: 建楼层流程的最后一步，greetings 对话和世界书全靠这个 save。失败时楼层建了但开场白和世界书静默丢失。

### [P2] 终端/focus/config 的 send completion 一律 `{ _ in }`
**文件**: `Services/CCBridgeWebSocketClient.swift:346-351, 362, 374-375, 385, 396`
**风险解释**: WS 未连时 attach 静默失败 → 终端黑屏，只能等重连后 resubscribeTerminals 兜底。reply 主链路的 send 错误是有意交给 grace timer 兜底（注释写明实测依据），不算问题；但终端链路没有等价兜底。

### [P2] handleIncoming 对畸形帧静默丢弃
**文件**: `Services/CCBridgeWebSocketClient.swift:457-460`
**风险解释**: hub 协议升级/发错帧时无任何日志（连 DEBUG print 都没有），排查"消息没到"只能上探针——「诡异 bug 早点加探针」的反模式温床。

### [P2] Preset 酒馆 JSON 往返丢正则脚本
**文件**: `Models/Preset.swift:203-206（导入读）vs 212-261（导出不写）`
**风险解释**: fromSillyTavernJSON 读 extensions.regex_scripts，toSillyTavernJSON 不输出 extensions。导入带正则的预设 → 导出分享/备份 → 正则全丢。toJSONString() 也用于"原始模式显示"，用户在原始模式看到的 JSON 缺数据，粘回去即丢失——预览/执行不同路的老坑变体。

### [P2] MCPStreamableHTTPTransport 不处理 Mcp-Session-Id
**文件**: `Services/MCP/MCPStreamableHTTPTransport.swift:23-50`
**风险解释**: MCP Streamable HTTP 规范要求客户端从 initialize 响应捕获 session id 并在后续请求带上；有状态 server 会对无 session 的后续请求回 400/404 → 表现为"initialize 成功但 tools/list 失败"。当前实测过的 server 是无状态的所以能通，兼容面有缺口。

### 其他
- heartbeat 用全量 tools/list 当 ping（MCPProvider.swift:326），每 12s 一次，对大目录 server 流量偏重，且结果直接丢弃——功能正确，效率债。
- MCPProvider.persist()/load() 的 try?（:293-305）：编码失败静默，配置可能悄悄不落盘。低风险。
- CCBridgeProvider 的 600s grace + hub replay + reply_id 去重 + message_id 精确匹配这套补丁链整体自洽，错位/重复投递的已知坑都有对应防御 ✓。

### [P2→总报告 P1-20] MCP server headers（常含 Authorization Bearer）与 oauthClientSecret 明文存 UserDefaults
**文件**: `Services/MCP/MCPProvider.swift:301-305` + `MCPModels.swift:128-130, 173-175`

**优先修复建议**：两条 P1（MCPClient.swift:99-122 与 MCPSSETransport.swift:81-93 的 continuation+TaskGroup 超时模式）是同一个错误模式的两处实例，修法相同——超时分支必须主动 resume 并移除 pending continuation，它们解释了"MCP 偶发卡死/SSE 连不上无报错"这一类症状。

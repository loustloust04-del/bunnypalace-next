## D3 并发安全

### D3-1 handleStickerDrop 在后台线程读共享可变状态
- 文件:行号：CardFlowView.swift:599-637（读点在 601-612）
- 严重度：P1
- 现状：`provider.loadItem(forTypeIdentifier:)` 的 completion 在非主线程执行，回调体内直接读 `viewModel.selectedConversation?.id`、`profileManager?.currentProfile.id`、`stickerVM.stickerAssets`，并调 `findNearestMessageId(y:)` → 遍历 `stickerVM.bubblePositions`（line 648）。只有最终写入包了 `DispatchQueue.main.async`（614）。
- 风险：`bubblePositions` 同时被主线程每个气泡的 `.task(id: midY)`（235）高频写入，后台遍历字典与主线程写是教科书式 data race（Dictionary 非线程安全，并发读写可崩）。SwiftData model（`selectedConversation`）跨线程读也违反 ModelContext 线程约束。

### D3-2 不可取消的 `DispatchQueue.main.asyncAfter` 链做滚动时序
- 文件:行号：CardFlowView.swift:163-171（scrollToLastMessage 三步），334, 348-353, 370-373
- 严重度：P2
- 现状：回底用 0.05s/0.5s 两段 asyncAfter，切对话场景 onChange/onAppear 又各包一层 0.05s。这些闭包持 `proxy`，不随对话切换取消。
- 风险：快速连续切对话时，上一对话的延迟 scrollTo 会打到新对话的 ScrollView 上（同名哨兵 id `__bottom_sentinel__` 永远存在，必然命中）；highlight 的 asyncAfter 有 id guard（129-131, 494-497），scroll 的没有，防御不一致。建议换 `.task + Task.sleep`（随 view 生命周期自动取消）。

### D3-3 handlePhotoSelection 用非结构化 `Task {}`
- 文件:行号：CardFlowView.swift:1078-1098
- 严重度：P2
- 现状：`Task { ... await item.loadTransferable ... await MainActor.run { selectedAttachments.append... } }`，不持引用、不取消。
- 风险：view 销毁（切对话）后任务继续跑并写已脱离的 `@State`；写丢静默。低概率低损害，但 `.task(id: selectedPhotoItems)` 是零成本的正确写法。

### D3-4 @MainActor 正确性
未发现显著问题（除 D3-1 外）。回调闭包都在主线程事件路径上触发；`InputFieldContainer`/`Coordinator`（IOSPromptTextView）的 delegate 回调天然主线程；`notifyHeightChange` 的 async 派发正确。

## D4 内存性能

### D4-1 `node.segments` 在单个气泡 body 内被解码 2-3 次
- 文件:行号：CardFlowView.swift:2199, 2266, 2301（articleModeBody）；ChatBubbleStyle.swift:158, 183, 209（BubbleModeRow：attachmentStrip + bubbleStack + isComplex）
- 严重度：P1
- 现状：`Conversation.swift:121-124` 证实 `segments` 是每次 access 都 `JSONDecoder().decode` 的 computed property（且 `segmentsData` 是 `.externalStorage`，access 还触发外部 blob 读）。articleModeBody 一次 render 顺序访问三处：附件条（2199）、user 分支（2266）、assistant 分支（2301）。BubbleModeRow 同样三处。
- 风险：带工具段/附件段的消息（CC 对话主力）滚动经过时每帧 2-3 次全量 JSON 解码 + 磁盘 blob 读；流式中带工具调用的消息每 token 重渲染都解一遍。应在 body 顶部 `let segs = node.segments` 取一次复用（articleModeBody 内 2199 取的 `segs` 没有传给 2266/2301，各自重新 access）。

### D4-2 流式期间 ContentCleaner 缓存 O(n²) 膨胀
- 文件:行号：CardFlowView.swift:2226；ChatBubbleStyle.swift:219；佐证 ConversationViewModel 1836-1838、ContentCleaner.swift:9
- 严重度：P1
- 现状：cacheKey 是 `"\(node.id)_\(node.content.count)"`；而流式时 `assistantNode.content = streamingText` 每 token 更新 → 每 token 生成一个新 key，value 是**整个前缀字符串**，存进无 `countLimit` 的 `NSCache<NSString, NSString>`。
- 风险：一条 1 万字的流式回复在缓存里堆出数千条 entry、约 O(n²) 字符总量（数十 MB 量级），NSCache 在 macOS 上极少主动驱逐。另注意此 key 形如 `id_count`，与项目规则"cacheKey 必须传 node.id"已分叉成两套 key（见 D4-3）。

### D4-3 `cacheKey: node.id` 的陈旧缓存 → 复制/朗读/预览出旧文本
- 文件:行号：CardFlowView.swift:2443, 2445, 2451, 2482, 2484, 2762；PinnedMessageBar.swift:90
- 严重度：P1（数据正确性，用户可感知）
- 现状：`ContentCleaner.clean` 命中缓存时不校验 text 本身（ContentCleaner.swift:14-17 直接返回 cached）。而 `node.content` 会被原地改写：流式逐 token（VM:1838）、CC `edit_message`（`ccEdited`，Conversation.swift:109）。「复制文本」「选择文本」用 `cacheKey: node.id`：
  ```swift
  NSPasteboard.general.setString(ContentCleaner.clean(node.content, cacheKey: node.id), forType: .string)
  ```
- 风险：消息流式中或被 edit_message 改过后，若 node.id 这个 key 曾在旧内容时被填充（pin bar 预览、分支选择器 2762 都用此 key），复制到剪贴板的就是**编辑前/截断的旧文本**。缓存键应纳入内容版本（如 D4-2 的 `_count` 后缀），或 clean 内部用 content hash 兜底。

### D4-4 `extractThinking` 每 render 编译正则 + 全文匹配，无缓存
- 文件:行号：CardFlowView.swift:2227；ChatBubbleStyle.swift:221；实现 ContentCleaner.swift:106-139
- 严重度：P1
- 现状：`NSRegularExpression(pattern:)` 每次调用新建，对全文跑 matches。articleModeBody 和 BubbleModeRow.parsedContent 每次 body 求值各调一次；流式每 token 一次。
- 风险：长消息流式时是 O(消息长 × token 数) 的正则开销，叠加 D4-1/D4-2 构成流式渲染的主要 CPU 热点。正则至少应 `static let` 缓存编译结果。

### D4-5 流式 onChange 无条件 scrollTo——每 token 拽回底部
- 文件:行号：CardFlowView.swift:356-360
- 严重度：P1（性能 + UX bug 双重）
- 现状：
  ```swift
  .onChange(of: viewModel.streamingText) { _, _ in
      if let lastId = viewModel.currentPath.last?.id {
          proxy.scrollTo(lastId, anchor: .bottom)
      }
  }
  ```
  没有 `isAtBottom` 检查。
- 风险：用户在长回复流式期间向上滚动想看历史，每个 token 都会被强制拉回底部——锁死阅读；同时每 token 一次同步布局滚动。手头就有现成的 `isAtBottom` state（47），加一个条件即可。

### D4-7 `UIImage/NSImage(data:)` 在 body 里反复解码

## D7 macOS 适配

### D7-1 macOS isAtBottom 用 LazyVStack 哨兵 onAppear，提前误判"到底"
- 文件:行号：CardFlowView.swift:244-247 vs iOS 路径 308-316
- 严重度：P2
- 现状：macOS 用哨兵 `Color.clear` 的 `onAppear/onDisappear` 驱动 `isAtBottom`；iOS 用 `onScrollGeometryChange` 精确计算。LazyVStack 会在哨兵进入可视区**之前**预实例化它（预载距离），onAppear 即触发。
- 风险：macOS 上接近底部但还差一屏内距离时回底按钮提前消失；两平台行为不一致。macOS 14+ 没有 onScrollGeometryChange（iOS 18/macOS 15 API），但可用 GeometryReader 哨兵 frame 判断。

### D7-2 Cmd+F 用 0×0 隐藏 Button 挂 keyboardShortcut
- 文件:行号：CardFlowView.swift:427-440
- 严重度：P2
- 现状：`.background { Button("")...keyboardShortcut("f", modifiers: .command).opacity(0).frame(width: 0, height: 0) }`。
- 风险：能用但脆弱——依赖该 view 在响应链上；macOS 正统做法是 App 层 `.commands { CommandGroup }`（还能进菜单栏让快捷键可发现）。多窗口时每窗口一个隐藏按钮倒是各自独立，行为碰巧正确。

### D7-3 NSSavePanel.runModal() 模态嵌模态
- 文件:行号：ExportOptionsSheet.swift:142-147
- 严重度：P2
- 现状：在 SwiftUI sheet 的按钮 action 里同步 `panel.runModal()`，阻塞主 runloop，save panel 浮在还开着的 sheet 上。
- 风险：体验粗糙（双层模态、sheet 不先收起）；`beginSheetModal(for:)` 或 SwiftUI `.fileExporter` 是正路。

### D7-4 PinnedMessageBar 用 onTapGesture 而非 Button
- 文件:行号：PinnedMessageBar.swift:58-59
- 严重度：P2
- 现状：`.contentShape(Capsule()).onTapGesture(perform: onTap)`，注释解释是为绕 iOS 26 interactive glass 吞 tap 的 bug。
- 风险：macOS 分支跟着一起失去键盘焦点与辅助功能 action（VoiceOver 不能激活）。iOS 的 workaround 不必拖累 macOS——macOS 分支可以用 Button。

### D7-5 多窗口草稿互踩（潜在）
- 文件:行号：CardFlowView.swift:39（view-local `@State draftText`）、478-480（willResignActive flush）
- 严重度：P2
- 现状：草稿是窗口私有 @State，flush 时整体覆盖 `conv.draftText`。WindowGroup 默认允许多窗口（未见限制），两个窗口开同一对话时后 flush 者赢。
- 风险：当前单窗使用习惯下不触发；若启用多窗需加协调。

### D7-6 右键菜单 / dark mode / hover
未发现显著问题。contextMenu 完整（2408-2472），剪贴板双平台分支正确；HoverButtons 用 `.opacity()` 控显隐符合项目规则（2605）；dark mode 由 ThemeManager 统一管理（MemoryPalaceApp.swift:521 `preferredColorScheme`），本集群无硬编码亮色假设（AttachmentPreviewSheet 纯黑底是设计意图，`.foregroundColor(.white)` 均在有色填充上）。macOS Cmd+Return 发送（1543-1550）正确实现。

```swift
    let chatHistory = (viewModel?.buildAPIMessages(maxMessages: preset.sampling.contextDepth) ?? [])...
```
- 风险: 2446 行单文件混合 5 种编辑模式 × 双平台 + 预览引擎。组装/请求预览每次 body 求值都同步 fetch 记忆、世界书并重建最多 200 条历史消息（见 D4）。预览复用实发链路（`ProviderRouter.previewRequestBody`）这点是对的（符合"预览必须复用真实执行路径"教训），但组装逻辑应该下沉到一个可注入的 service。

**F2. onAppear 里做数据迁移/实例化写操作**
- 文件: `PersonaSettingsTab.swift:249`、`:259-262`（ensureFloorInstance）

- 风险: "漏网数据兜底"这种 schema 修复放在某个设置 tab 的 onAppear，意味着只有用户打开过这个页才被修复；其他读 presetId 的路径在修复前都拿到悬空 id。应放在 ProfileManager/PresetManager 启动时。

**F3. macOS「朗读」「附件」tab 渲染的是整个 GeneralSettingsTab**
- 文件: `MemoryPalace/Views/SettingsView.swift:203-208`

```swift
case .general: GeneralSettingsTab()
case .tts:     GeneralSettingsTab()
```

- 风险: macOS 点「朗读」或「附件」tab 看到的是含楼层切换、气泡标签、世界书绑定的完整通用页，tab 语义失效；iOS 端却有独立的 IOSTTSPage/IOSAttachmentPage，两端结构分叉。

**F4. @AppStorage 完全散落，无集中 key 管理**
- 文件: 全集群（典型: `AppearanceSettingsTab.swift:8-28` 与 `:339-358` 两份各 17 个 key 重复声明；`MemorySettingsTab.swift:364-375` 12 个 `mem_*` key）
- 维度: D1/D6 | 严重度: P2
- 风险: 默认值靠肉眼保持一致（如 `fontScale = 1.2`、`bubbleSpacing = 31`），一处改默认另一处忘改即出现平台间行为分裂；key 拼错编译器不报。

**F5. 视图里硬编码本机 worktree 绝对路径**
- 文件: `APISettingsTab.swift:546-549`
- 维度: D1/D7 | 严重度: P2
- 现状: `URL(fileURLWithPath: "/Users/susu/Desktop/susu-project/记忆宫殿/MemoryPalace/.claude/worktrees/cc-bridge/cc-bridge/README.md")`（有 TODO 标注）
- 风险: 任何非本机环境（甚至本机删掉该 worktree 后）按钮打开失败且无提示。与「App 必须自包含」教训冲突。

## D2 SwiftData（profileId predicate）

**未发现显著问题。** 集群内所有 fetch 均带 profileId（或 id）predicate，无 `FetchDescriptor<MessageNode>()` 无条件全量 fetch：GeneralSettingsTab.swift:149 WorldBook 按 profileId；StickerSettingsTab.swift:102-110 按 profileId；DataSettingsTab.swift:395、:481 按 `profileId && !isDeleted`；MemoryService listAll/listHot 均带谓词（已验证实现）。集群内未用 `@Query`（全部手动 fetch + @State），规避了楼层切换时 @Query 不带新 predicate 的问题；MemorySettingsTab 还接了 `.profileWillSwitch` 通知清空列表（:198-200），是有意识的 race defense。

## D3 并发安全

**F6. 模型拉取的过期响应竞态：切换 provider 后旧请求结果照常落地**
- 文件: `APISettingsTab.swift:1038-1057`
- 维度: D3 | 严重度: P2
- 现状: `apiAutoFetchModels()` 的在途 Task 没有取消、落地时也不校验 `providerId == effectiveProviderId`。
- 风险: 慢请求后到会把 A 家的模型列表显示在 B 家名下。`testProvider` 同样无取消（结果按 providerId 入字典，危害较小）。

**F7. SlotEditPage 用构造时捕获的 index 写回最新 preset**
- 文件: `PersonaSettingsTab.swift:2174-2178`（patch）、`:2286-2292`（删除）
- 维度: D3 | 严重度: P2
- 现状: `guard var p = psm.preset(byId: preset.id), index < p.prompts.count else { return }; mutate(&p.prompts[index])`——按 index 而非 slot.id 定位。
- 风险: 编辑页打开期间 prompts 数组被别处增删/重排，`index < count` 守卫通过但写到错误插槽。应按 `firstIndex(where: { $0.id == slot.id })` 定位。

**F8. JSON 模式 dirty buffer 跨 preset 应用**
- 文件: `PersonaSettingsTab.swift:1252-1257`（onAppear 守卫）+ `:1260-1272`（applyRawJSON）
- 维度: D3/D5 | 严重度: P2
- 现状: buffer 为 dirty 时切换预设（顶部 Picker 随时可切），buffer 不刷新；此后点「应用」`parsed.id = preset.id` 会把旧预设的 JSON 内容整体写进新选中的预设。
- 风险: 静默串台覆盖。切 preset 时应清 dirty buffer 或弹确认。

正面: iOS 简单模式草稿系统（:2049-2062 防抖 + onDisappear flush + Task.cancel）和 iOSSimpleVisibilityTask 的取消处理规范；@MainActor 标注正确；DataSettingsTab 后台导出用 `ModelContext(container)` 新建上下文、主线程回写进度，模式正确。

## D4 内存/性能

**F9. 每个键击触发全量预设 JSON 序列化写 UserDefaults**
- 文件: `PersonaSettingsTab.swift:836-849`（personaSlotField binding set）、`:1163-1166`（slotContentEditor TextEditor）、`:326-448`（14 个采样参数 binding 同模式）；落点 `MemoryPalaceApp.swift:306-312, 343-347`
- 维度: D4 | 严重度: **P1**
- 现状: macOS 的 TextEditor 直绑 `psm.save(p)`，每输入一个字符就把**全部模板+全部楼层实例**整体 encode 写 UserDefaults，且 `presets` 是 @Observable 数组，整体替换触发 personaTab 全量重渲染。
- 风险: 预设库一大，打字肉眼可见卡顿。iOS 端已做 300ms 防抖草稿（说明作者意识到了），macOS 端没有同等处理。

**F10. 组装/请求预览在 body 内同步做重活，无缓存**
- 文件: `PersonaSettingsTab.swift:1276-1278`（assembly）、`:1311-1312`（request）

- 现状: 2 次 SwiftData fetch + `buildAPIMessages(maxMessages: contextDepth≤200)` + 全段 token 估算 + JSONSerialization prettyPrinted 直接在 view-building 函数体里执行。
- 风险: 大对话 + 高上下文深度时预览 tab 交互卡顿；展开/收起段落这种纯 UI 操作不应重新组装。

**F11. GeneralSettingsTab 在 body 里做 fetch**
- 文件: `GeneralSettingsTab.swift:147-150`、`:294-297`
- 维度: D4 | 严重度: P2
- 风险: 数据量小实害低，但与集群其他页"onAppear 加载进 @State"的模式不一致。

**F12. 巨型 body 不拆分**
- 文件: `PersonaSettingsTab.swift:326-813`（personaSamplingSection 单函数约 490 行）；`APISettingsTab.swift` 单 struct 1085 行

## 安全专项（API key）

**F27. MCP OAuth Client Secret 与自定义 Headers 明文存 UserDefaults**
- 文件: 入口 `MCPSettingsView.swift:18-41, 448-449`；持久化 `Services/MCP/MCPProvider.swift:301-303`、`Services/MCP/MCPModels.swift:128-130, 139-141`
- 维度: 安全 | 严重度: **P1**
- 风险: 项目已有 KeychainStore 且 API key 全部走 Keychain，唯独 MCP 这条新路径把等价凭证（headers 常含 `Authorization: Bearer xxx`）落回明文 plist，随备份外泄。建议按 `mcp-{serverId}` account 存 Keychain。

**F28. OAuth Client Secret 用明文 TextField 输入**
- 文件: `MCPSettingsView.swift:449`
- 维度: 安全 | 严重度: P2
- 现状: 普通 TextField 屏幕明文回显。对照 APISettingsTab:415 和 cc-bridge token :503 都用了 SecureField。

**其余安全面正面确认**：API key 存取全部经 KeychainStore + SecureField；两条遗留明文迁移路径均"搬进 Keychain 后删除原值"；grep 全仓未发现任何 print 输出 key/token 值；cc-bridge 扫码配对 token 写 Keychain、URL 写 UserDefaults，分界正确。

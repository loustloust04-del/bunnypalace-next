## D2 SwiftData（重点）

### F1.【P0】`@Attribute(.unique)` id 在单 container 下跨楼层 upsert，导入/迁移可静默"偷走"另一楼层的对话
- **文件**: `Models/Conversation.swift:14,82`（unique 声明）；被触发于 `Services/ConversationImporter.swift:49-52,76-87`、`Services/ClaudeImporter.swift:94-97,124-135`、`Services/UnifiedContainerMigration.swift:154-212`
- **维度**: D2 + 数据安全专项
- **现状**: Conversation 与 MessageNode 都是 `@Attribute(.unique) var id: String`，而导入器的去重只查**当前楼层**（`#Predicate { $0.profileId == scopedProfileId }`）。
- **风险**: SwiftData 对 unique 冲突的 insert 行为是 upsert（更新现有行的全部属性，包括 profileId）。把同一份 conversations.json 导入楼层 B 时，若楼层 A 已有同 id 对话，insert 不会报错也不会重复——而是把楼层 A 的那行 `profileId` 改写成 B，**楼层 A 的对话和全部 MessageNode 静默消失**。迁移同理：当年 per-profile store 时代同一导出文件进过两个楼层的话，后迁的 profile 会把先迁的行 upsert 走。merge 导入插入新节点时同样可能把别的楼层的同 id 节点"抢"过来，导致那边树断裂。触发条件"同一导出进多个楼层"对实际使用方式完全现实。这是路线 B 架构与 unique 约束的根本冲突，建议复合唯一（profileId+id）或去掉 unique 由导入层保证。

### F2.【P1】迁移：legacy store 打开失败被 `continue` 跳过，最后仍置 doneKey=true，永不重试
- **文件**: `Services/UnifiedContainerMigration.swift:62-70, 98-99`
- **维度**: D2 / D5
- **现状**: catch 分支 print 后 continue；循环结束无条件 `UserDefaults.standard.set(true, forKey: doneKey)`。
- **风险**: 某楼层 legacy store 因 schema mismatch / 磁盘错误打不开时，该楼层数据留在 legacy 文件里，但 done 标记照常落下——该楼层在 app 里表现为空楼，且没有任何用户可见报错。对比：per-entity 迁移 throw 会冒泡到 `MemoryPalaceApp.swift:402-407` 被 catch、doneKey 不落、下次启动幂等重跑——这条路径是对的，唯独 open-failure 这条是错的。

### F3.【P1·磁盘实证】WAL/SHM sidecar 改名扩展名写错（`.wal` vs `-wal`），sidecar 从未随备份搬走；且 rename 时 legacy container 仍在打开状态
- **文件**: `Services/UnifiedContainerMigration.swift:110-129`
- **维度**: D2 + 数据安全专项
- **现状**: `url.appendingPathExtension(ext)` 产生 `xx.store.wal`，Core Data SQLite sidecar 实际命名是 `xx.store-wal` / `xx.store-shm`（连字符）。`fileExists` 永远 false，move 从不执行。且 `renameLegacyToBackup` 在循环体内调用（:92），此时 legacyContainer 还活着、连接未关闭，主库文件在打开状态下被 move。
- **风险**: 磁盘实锤：`~/Library/Application Support/MemoryPalace/` 下 `275202A6….store.backup-2026-04-22` 旁边躺着孤儿 `275202A6….store-shm` / `-wal`。备份文件缺 WAL——rename 时未 checkpoint 的事务不在备份主文件里（APFS 下大概率靠连接关闭时的 checkpoint 写进了改名后的文件，但这是运气不是设计）。"永久保留的备份"完整性没有保障。

### F4.【P1】搜索主线/分支过滤是 N+1 全量节点 fetch
- **文件**: `Services/SearchService.swift:168-198`
- **维度**: D2 / D4
- **现状**: 对每个命中关键词的对话，单独 fetch 一次 Conversation + 一次该对话**全部** MessageNode 来算 mainPathSet。
- **风险**: 常用词命中几百个对话时是几百次往返、每次把整条对话的节点（含 content 字符串）拉进内存。computeMainPathSet 只需要 id/parentId/childrenIds/currentNodeId，拉全 content 是浪费（propertiesToFetch 可解）。

### F5.【P1】全项目无 VersionedSchema / SchemaMigrationPlan
- **文件**: 全项目 grep `VersionedSchema|SchemaMigrationPlan|MigrationStage` = 0 命中
- **维度**: D2
- **风险**: 目前都是"加可选字段/带默认值字段"所以没炸。一旦需要改名、改类型、拆表，lightweight migration 直接失败，而 20 万节点的用户库没有版本化迁移路径可走。

### F6.【P2】`findStickersNearMessage` 踩 optional 字段 predicate 陷阱——所幸是死代码
- **文件**: `Services/SearchService.swift:523-534`；`Models/PlacedSticker.swift:18`
- **现状**: `#Predicate<PlacedSticker> { s.nearestMessageId == mid && s.profileId == pid }`——optional 字段 == 值的 #Predicate 静默匹配不到。grep 确认全项目无调用方（死代码）。同文件 searchPlacedStickers:475-480 对同一字段刻意走了内存 filter，说明陷阱是已知的，这处是漏网。建议直接删或修。

### F7.【P2】`#Index` 全部包在 `#if os(iOS)` 里，macOS 端 profileId fetch 全表扫
- **文件**: `Models/Conversation.swift:6-12, 74-80` 等
- **风险**: 本集群所有按 profileId/conversationId 的 fetch 在 macOS（本体平台、20 万节点所在地）没有索引支撑。macOS 15+ 用户也被一刀切排除。（总报告升级为 P1-4）

### F8.【P2】MemoryStore 的 update/delete/recordAccess 仅按 UUID fetch，不带 profileId
- **文件**: `Services/MemoryService.swift:48-68, 100-110`
- **风险**: 动作来源是 LLM 输出的 JSON。UUID 碰撞几乎不可能，但这是"所有 fetch 必须带 profileId"纪律的例外点，加守卫零成本。

其余 D2 检查结论：**reviewed 文件内 profileId 谓词覆盖完整**；optional createTime 陷阱在 SearchService.swift:150-153、215-218 有明确注释规避；导入批量插入有 200 条/批 save、迁移 MessageNode 有 500 条/批 save；搜索不加 fetchLimit 是粟粟的明确要求（不算问题）。

## D3 并发安全

### F9.【P1】ModelContext 在 nonisolated async 函数中跨 await 悬挂点使用，未用 @ModelActor
- **文件**: `Services/ConversationImporter.swift:45,106-117`、`Services/ClaudeImporter.swift:90,154-165`；入口 `Views/ImportView.swift:678,689`（Task.detached）
- **现状**: `let context = ModelContext(modelContainer)` 后，循环里每批 `try context.save()` → `await updateProgress(...)`（hop 到 MainActor）→ 回来继续用同一 context。
- **风险**: 单 Task 内顺序访问，没有真正的数据竞争；但每个 await 之后 continuation 可能落在协作池的不同线程，ModelContext 非 Sendable。今天能跑，Swift 6 strict concurrency 直接编译不过，属于"碰巧没炸"。规范做法是 @ModelActor 包导入器。

### F10.【P1】searchStickers 把活的 PersistentModel 从临时后台 context 抛回调用方
- **文件**: `Services/SearchService.swift:402-445`（返回 `[StickerAsset]`）；`:523-534`（返回 `[PlacedSticker]`，死代码）
- **现状**: DispatchQueue.global 闭包内建临时 context，fetch 出模型对象经 continuation 返回；闭包结束 context 即释放。
- **风险**: 调用方（MainActor 上的 view）随后访问这些对象的属性，等于在宿主 context 已销毁后触发 fault——SwiftData 已知崩溃/脏读模式。对比同文件 performSearch/searchPlacedStickers/searchMemories 都正确地转成了值类型 struct 再返回——searchStickers 是唯一漏网。

### F11.【P2】导入与摘要任务均无取消支持；摘要存在 last-wins 竞写
- **文件**: ConversationImporter/ClaudeImporter（全文无 Task.isCancelled 检查）；`Services/ContextSummarizer.swift:125-205`
- **风险**: 大文件导入一旦开始无法中止；ContextSummarizer 连续两次发消息会并发跑两个 summarize 对同一 UserDefaults key 双写——写入的 struct 是原子整体，最坏覆盖率回退一轮、下轮自愈，可接受但值得知道。

## D4 内存性能

### F12.【P1】迁移把 legacy store 的 20 万 MessageNode 一次性全量 fetch 进内存
- **文件**: `Services/UnifiedContainerMigration.swift:182`
- **现状**: `let olds = try legacyCtx.fetch(FetchDescriptor<MessageNode>())`——olds 数组强持有全部对象（含全部 content 字符串）直到该 profile 迁完；500 条/批 save 只缓解了写侧，读侧没有分页也没设 fetchBatchSize。
- **风险**: 主力楼层迁移瞬时内存 = 整库文本体积。macOS 上大概率挺得过（已实际迁完），但这是项目"禁止无条件全量 fetch MessageNode"红线的字面违例，且 iOS 端复用此代码会 OOM。

### F13.【P1】导入器注释自称 "Streams ... in batches"，实际整文件一次性 decode
- **文件**: `Services/ConversationImporter.swift:4,33-37`；`Services/ClaudeImporter.swift:78-82`
- **现状**: `Data(contentsOf: url, options: .mappedIfSafe)` + `decoder.decode([RawConversation].self, from: data)`。
- **风险**: mmap 只省了原始字节，decode 产物（全部对话+节点的 Swift 对象图，含 AnyCodable 嵌套）全量驻留，再叠加 incoming.nodes 的二次拷贝。几百 MB 的 ChatGPT 导出内存峰值数倍于文件大小。batch 只 batch 了 SwiftData 写入。注释与实现不符。

### F14.【P2】ContentCleaner cacheKey 规则已遵守，但 node.id 作 key 无内容版本，跨 call-site 策略不一致
- **文件**: `Utils/ContentCleaner.swift:12-14`；call sites: `Services/SearchService.swift:202`（node.id ✓）、`Views/CardFlowView.swift:2226` 与 `Views/ChatBubbleStyle.swift:219`（`id_count`）、`Services/MarkdownExporter.swift:242,301`（nil → hashValue 兜底）
- **风险**: 红线（cacheKey 传 node.id）已满足。但 merge 导入或消息编辑改变 content 后，凡用裸 node.id 的位置会吐**重启前的旧清洗结果**；CardFlow/ChatBubble 已用 `id_count` 自行规避，说明 stale 问题踩过却只修了两处。三种 key 策略并存是隐性 DRY 债。

### F15.【P2】MemoryInjector 关键词匹配的重复计算
- **文件**: `Services/MemoryService.swift:224-237`
- **现状**: matchesKeyword 与 hitScore 各自 `messages.joined(...).lowercased()`（每条 memory 重复一次）。
- **风险**: 每轮发消息触发，memory 几百条时是 O(N×对话长度) 的重复字符串工作。haystack 应在循环外算一次。

### F16.【P2】SearchService 多处"fetch 全部再内存过滤"
- **文件**: `SearchService.swift:248-253`（内容桶为建 convMap 再次拉全 profile Conversation）、`:425-431`（tags 搜索拉全量 StickerAsset）、`:470-497`、`:741-749`
- **风险**: 各处单表数量级可控，是有意识的取舍（数组字段 predicate 写不了，有注释）；但 :248 那次本可用已拿到的 convId 集合收窄。

## D5 错误处理

### F17.【P1】导入中途失败：已落库的批次不回滚，ImportRecord 永远停留在 supportsUndo=false → 部分导入既删不掉也撤不了
- **文件**: `Services/ConversationImporter.swift:106,119-126,137-139`（ClaudeImporter 同构）；`Models/ImportRecord.swift:26`
- **现状**: 每 200 条 `try context.save()`；任何一批 throw → 直接 failImport(error)，没有 rollback()，而 record 的计数和 `supportsUndo = addedConversations > 0` 要到全部循环结束后才写。
- **风险**: 失败时刻之前的批次已持久化，但 record 是默认值——UI 按 supportsUndo 过滤后不给撤销入口，partial 数据成了挂在死 record 上的孤儿。好的一面：重新导入同文件会按 id skip 已入库的，不会产生重复。缺的是清理/续传路径。

### F18.【P2】undo 路径静默吞错
- **文件**: `Views/ImportHistoryView.swift:110-146`（调用 ImportSupport.restoreConversationChange）
- **风险**: 部分撤销态对用户不可见。好的一面：失败时 change 行未删，重跑 undo 是幂等的——只是用户不知道要重跑。

### F19.【P2】`try?` 吞错误清单
- `SearchService.swift:179,183,253,325,350,365,373,422,428,466,473,487,496,533,647,736,744`（所有搜索 fetch 失败 = 显示空结果）；`ClaudeImporter.swift:485`（segments encode 失败静默退回无分段渲染）；`ContextSummarizer.swift:22-28`；`ConversationViewModel.swift:2115`（`try? MemoryExtractor.executeActions`——记忆写库失败但 UI 照样弹"记住 N 条"胶囊，**反馈与事实可能不符**）
- **风险**: 搜索场景"查不到"与"查挂了"不可区分；记忆胶囊那条最值得修。

### F20. 迁移失败时用户数据安全——结论偏正面
- runMigration 的 per-entity throw 会冒泡被 catch、doneKey 不落、legacy 文件不动、下次启动 clearProfileData 幂等清残留再重跑——**中断不丢数据、不留重复**，设计正确。唯二缺口是 F2（open 失败置 done）和 F3（备份缺 sidecar）。另：inProgressKey（:20,48,98）只写从不读，是死状态键。

## D6 代码卫生

### F21.【P1】ConversationImporter 与 ClaudeImporter ~400 行结构性复制
- **文件**: 两文件的 beginImport/updateProgress/finishImport/failImport/progressStatusText/completionStatusText（ConversationImporter.swift:307-453 ≈ ClaudeImporter.swift:376-561 几乎逐字相同），importFile/mergeImportFile 主循环骨架也是同一份模板

### F22.【P2】completionStatusText 在完成时刻显示"…处理中"
- **文件**: `ConversationImporter.swift:436-453`、`ClaudeImporter.swift:544-561`——一闪而过的死文案。

### F23.【P2】ClaudeImporter 完成文案的无意义分支
- **文件**: `ClaudeImporter.swift:181-195`——两个分支实参在 added==0 时完全等价，三元表达式可整段删掉。

### F24.【P2】死代码/死状态
- `SearchService.swift:523-534` findStickersNearMessage 无调用方（且自身带 F6 的 bug）；`UnifiedContainerMigration.swift:20` inProgressKey 只写不读；`ScopedFetch.swift:23-25` HasProfileId 协议无任何泛型约束使用（纯文档标记，文件名 "ScopedFetch" 名不副实）。

### F25.【P2】magic number / 阈值双源
- 200/500 批量各自硬编码；**hot 0.3 / warm 0.05 在 `MemoryService.swift:71,83`（predicate 用落库 decayWeight）与 DecayEngine.tier（:156-161，用惰算 effectiveWeight）各写一份**——两边阈值同值不同语义，改一处忘另一处会出现"列表说是 hot、tier 说是 warm"的不一致。

### F26.【P2】两套 token 估算器口径不一致
- `Models/Memory.swift`（中文×1.5 实现为非 ASCII +2）vs `Utils/TokenEstimator.swift:11-24`（CJK×1.0）——Memory 的 tokenCount（预算扣减用）与保险闸的估算对同一段中文差 50%，2000 token 记忆预算的实际松紧取决于走哪个估算器。

### F27.【P2】MemoryExtractor.buildPrompt 手拼 JSON 不转义
- **文件**: `MemoryService.swift:314-317`——content 含引号/换行时拼出非法 JSON 喂给 LLM。只影响提取质量，JSONEncoder 一行可解。

### F28.【P2】无 id 对话每次导入生成新 UUID → 重复导入会重复入库
- **文件**: `ConversationImporter.swift:392`：`let conversationId = raw.id ?? UUID().uuidString`；同行 `:408-409` 的 `create_time ?? 0` 会让缺时间戳的对话排序到 1970。

### F29.【P2·低置信，需实测确认】Claude 首条消息的 parent sentinel
- **文件**: `ClaudeImporter.swift:465-471`——只判空串，Claude 导出首条消息的 parent_message_uuid 通常是 root sentinel UUID（非空、不对应任何节点），于是根节点 parentId ≠ nil。实际导入能用说明树构建端容忍了悬空 parent；但任何依赖 `parentId == nil` 判根的新代码都会在 Claude 数据上翻车。值得在树构建端确认容错语义并加注释。

### 数据安全专项·undo 快照完整性——结论：基本完整 ✓
- ConversationSnapshot/MessageNodeSnapshot 覆盖了 merge 实际会改写的全部字段；未快照的字段 merge 也不会动 → undo 不会误伤用户后续状态。唯一缺口：undo 时若对话已被整体删除，重建会丢未快照字段（isPinned、ccMessageId 等）——边缘场景，可接受。
- 顺带：merge 模式下每个被更新对话的**全部节点 JSON 快照**永久存在 change 行里（ClaudeImporter.swift:263-272），大库反复 merge 会让 store 体积显著膨胀，没有任何清理旧 ImportRecord/Change 的机制。P2 记一笔。

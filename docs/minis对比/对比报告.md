### 洞 1 · `fs_write` 缺 `content` 会把已有文件清空 🔴 数据丢失

`FileLibraryTools.swift:227` 的参数取值 helper 把缺失字段一律降成空串：

```swift
private static func str(_ d: [String: Any], _ k: String) -> String { d[k] as? String ?? "" }
```

`fs_write` 分支直接把它交给原子写（`FileLibraryTools.swift:73-77`）：

```swift
case .write:
    let path = str(args, "path")
    let before = try? FileLibraryStore.read(path, profileId: profileId)
    try FileLibraryStore.write(path, content: str(args, "content"), profileId: profileId)
```

**后果**：模型发出一个合法 JSON `{"path":"日记.md"}`（缺 `content`），MP 不报错、不拒绝，直接把 `日记.md` 写成空文件。`before` 变量证明这条路径本来就覆盖已有文件。JSON 整个解析失败时还会降成空字典 `?? [:]`（`FileLibraryTools.swift:45`），同样往下走。

**Minis 怎么做**：调用前用模型刚看过的同一份 schema 做 required 校验，缺参/null/不允许的空串一律拦下（`Agent/Chat/AIChatViewModel+ToolPreflight.swift:203-281`）；参数流被截断时**明确拒绝执行写类工具**，宁可让模型重发（`+ConcurrentTools.swift:186-240`）。

**建议**：加 `ToolCallPreflight`，从 `ToolDefinition.required` + MCP schema 取约束，在所有 executor 之前统一校验，失败作为 `isError` 结果回灌给模型自愈。第一版只做确定性拒绝，不做模糊修复。`new_string == ""` 这类「空串是合法语义」的字段要走白名单。**代价：天级。这是本批次第一优先级。**

### 洞 2 · 摘要跨分支污染 🟠 正确性

`SummaryFileStore` 一个对话只存**一份**摘要，按 conversationId 前 8 位寻址（`SummaryFileStore.swift:19-21, 36-42`），元数据只有三个字段（`SummaryFileStore.swift:76-81`）：

```swift
("conversationId", conversationId),
("coveredCount", String(summary.coveredCount)),
("updatedAt", ...),
```

**没有 anchor node id，没有分支路径指纹**。而 MP 的消息是树（`Conversation.swift:94-114` 的 `parentId`/`childrenIds`），切分支只改 `branchChoices` 重建 `currentPath`。

**后果**：在分支 A 生成的摘要，切到分支 B 后**照样被注入**——因为寻址只看 conversationId。分支越用越多，污染越重。自动摘要还会把当时的 `currentPath` 拍进 detached task 写回同一文件，切分支时既不取消也没有 stale-write 守卫。

这条对粟粟尤其相关：**分支树是 MP 的核心资产，用得越狠这个 bug 咬得越深**，而且它污染的是「AI 记得什么」——症状会表现为「它怎么把另一条线的事记岔了」，很难归因到摘要。

**建议**：摘要记录带 `anchorNodeId` + root→anchor 的稳定 path fingerprint；只在当前路径仍含同一锚且指纹匹配时注入；异步写回比较 generation token，旧路径任务晚到就丢弃。Minis 的线性 `lastCompactedMessageId` 方案**不能直接搬**（它的会话是线性的，fork 是整会话拷贝）。**代价：周级。**

### 洞 3 · 工具循环的中间请求既不记账也不 gate 🟠 花钱

`onToolCalls` 的签名不带 usage（`ChatService.swift:47`）：

```swift
internal var onComplete: ((String, TokenUsage?) -> Void)?
internal var onToolCalls: (([ToolCallBlock]) -> Void)?   // ← 没有 TokenUsage
```

工具回灌直接递归再发请求，中间没有预算预检（`ConversationViewModel.swift:2886-2893`）。

**后果**：一个 8 轮工具 turn = 最多 9 次模型请求，其中只有最后一次（`onComplete`）入账。**中间 8 次的 token 花了但不记、不 gate**。全局预算闸（`GlobalBudgetStore` + `BudgetCalculator.swift:60-78`）是活的、默认开的，但它只看得见冰山一角。

顺带确认一个小偏差：`guard round < maxToolRounds` 在工具**执行完之后**才检查（`ConversationViewModel.swift:2876`），round 从 0 起，所以实际是执行 9 批才停，文案说 8 轮。

**建议**：provider 的 tool-call 终止事件也带 usage 回来，立即 commit；下一次回灌请求前重新 gate。单位继续用 USD（MP 多 provider 多价位，这个选择比 Minis 更合适），另记 request count / round。**代价：天级。**

### 洞 4 · 一个未知 provider type 会清空全部 API key 配置 🟠 数据可见性

`ProviderType` 是没有 unknown case 的 `String, Codable` enum，只有四个值（`APIProvider.swift:5-10`）。而 `loadCredentials` 解码失败时整表变空数组（`APIProvider.swift:1162-1164`）：

```swift
return (try? JSONDecoder().decode([APICredential].self, from: data)) ?? []
```

**后果**：任何一条 credential 带未知 type，**整张凭据表读成空**——用户看到的是所有 API key 都不见了。触发条件不是日常路径（要么装了新版加了第五个 case 再回退旧版，要么导入了含未知 type 的配置），但一旦触发是全量的。

**Minis 怎么做**：未知 raw type 映射成 `.unsupported` 而非抛错，并保留原始字符串在 encode 时原样写回（`Providers/ProviderTypes.swift:22-33`、`ProviderInstance.swift:88-130`）。

**建议**：自定义 decode + unknown sentinel + 保留 `unknownProviderTypeRaw`；UI 显示「当前版本不支持」但不删不改写。迁移绝不能把 unknown 自动降级成 `.openaiCompatible`（会往错误端点发请求）。**代价：小时级。这是投入产出比最高的一条。**

### 洞 5 · MCP 的 OAuth 是个配置壳，填了不生效 🟡 误导 UI

`MCPServerConfig` 有 `oauthClientId` / `oauthClientSecret` 字段，设置页也让用户填（`MCPModels.swift:122-164`、`MCPSettingsView.swift:472-476`），secret 还会被清洗进 Keychain。但 transport 工厂只消费 url + headers（`MCPTransport.swift:12-20`）：

```swift
case .sse:
    return try MCPSSETransport(serverURL: config.url, headers: config.headers)
case .streamableHTTP:
    return try MCPStreamableHTTPTransport(serverURL: config.url, headers: config.headers)
```

全仓搜这两个字段，命中只在模型定义、设置表单、增删改和持久化——**没有授权 URL、没有 PKCE/state、没有 token 交换、没有把 token 注入 transport 的路径**。

**后果**：用户填完 client id/secret 以为配好了，连接时什么都不会发生。

**建议**：短期至少把 UI 标注「暂未支持」或隐藏；要做就按 MP 架构原生实现 static PKCE（授权/token endpoint + scope + redirect，token 进现有 Keychain，连接前取 token 组 Authorization header，401 走单飞 refresh）。Minis 的实现可对照（`Agent/Session/MCPOAuthController.swift:269-385`），但**不要搬它的 guest token bridge**——它为了让 Linux 沙箱里的 daemon 自己刷新，把 token 明文写进 guest 可见 JSON；MP 是原生 transport，token 该留在 Keychain。**代价：小时级（标注）/ 周级（实现）。**

### 洞 6 · 同步/备份还原会跨楼层偷数据 🟠 数据错位（已知教训的未修残留）

`BackupStore.restoreConversation` 查重时按 profileId 缩了范围（`BackupStore.swift:424, 462`）：

```swift
predicate: #Predicate<Conversation> { $0.id == convId && $0.profileId == pid }
```

`SyncStore.importAll` 同形（`SyncStore.swift:511-557, 559-595`）。

**后果**：这正是 `feedback_swiftdata_unique_upsert` 那条教训的形状。`Conversation.id` 是**全库** unique，`profileId` 只是普通列。如果同一个 id 存在于**另一个楼层**，这个 scoped 查询返回空 → 走 insert → SwiftData 的 unique 冲突不报错而是 **upsert**，把那一行的全部属性（**含 `profileId`**）改写成新值 → 另一楼层的对话被静默偷到当前楼层。

**关键是 MP 自己已经有正确解法**，注释里写的就是这条教训（`ImportSupport.swift:26-33`），函数是 `crossProfileConflictedConversationIds`（`ImportSupport.swift:80`），分批 IN 查询、不全量 fetch。它被四处导入路径正确调用：`ConversationImporter.swift:79, 235`、`ClaudeImporter.swift:124, 287`。

**漏的是同步和备份还原这两条路径。** 教训学到了、导入修了、还原路径没跟上。

**建议**：`SyncStore.importAll` 和 `BackupStore.restore` 在 insert 任何 Conversation/MessageNode 前调用已有的 `crossProfileConflictedConversationIds`；一份对话里任一 id 冲突就**整份跳过**或整份确定性改 id（conversation + node + parentId + childrenIds + currentNodeId 一起改），禁止部分 insert 后才发现冲突。前置要先定清语义：「全库还原」可以覆盖 profile 归属，「单楼层/单对话还原」不该抢别的楼层的行。**代价：天级。**

### 洞 7 · 点了别的楼层的通知，app 打开后什么都不发生 🟠 日常路径

`ContentView.consumePendingPushTarget`（`ContentView.swift:705-712`）三个问题叠在一起：

```swift
guard let chatId = UserDefaults.standard.string(forKey: "pendingPushChatId"), !chatId.isEmpty else { return }
UserDefaults.standard.removeObject(forKey: "pendingPushChatId")   // ① 先删，无重试机会
let pid = profileManager?.currentProfile.id ?? ""                  // ② 当前楼层
let desc = FetchDescriptor<Conversation>(predicate: #Predicate<Conversation> { $0.id == chatId && $0.profileId == pid })
guard let conv = try? modelContext.fetch(desc).first, !conv.currentNodeId.isEmpty else { return }  // ③ 静默 return
```

**后果**：推送里的 `chat_id` 是**全局 unique** 的 `Conversation.id`，真实楼层归属在 `profileId`（`Conversation.swift:14-21`）。当通知属于**非当前楼层**的对话时，这个 scoped fetch 返回空 → 静默 return，而 pending key 已经被删掉了。用户看到的是：**点了通知，app 打开，什么都没发生，再点也没用。**

这是日常路径——楼层 A 的 AI 推了消息、用户当时停在楼层 B，就会撞上。

**建议**：先按全局 unique 的 id 查出这条对话真实的 `profileId`；不同就先调 `switchTo` 切楼层、等新 subtree 就绪再导航；**成功或明确 terminal failure 之后才消费 pending key**。注意 `switchTo` 会同步广播清旧 SwiftData 引用再切 currentProfile（`MemoryPalaceApp.swift:206-221`），路由必须尊重这个时序。往下走就是 §二 C2 的统一 `AppRoute`。**代价：天级。**

### 洞 8 · 流式每 token 完整重 parse / 重建 body ⚪ CPU 债，**不是体验债**（09-02 修正）

> **⧫ 粟粟 09-02：「我们流式现在也平滑的要死了」——对。本条原写「长回复会越来越卡」是观感措辞，错了。以下是修正版。**

**观感层 MP 早已解决，且解法比 Minis 走得更远。** `StreamPacer.swift:3`：「流式显示节拍器：到达文本（provider 每 ~0.1-0.6s 一坨）和显示文本解耦」，显示文本按 30Hz 追赶到达文本（`CardFlowView.swift:3003`），`ChatService.swift:121`：「节拍器把空档填成连续打字」。Minis 那句「逐字顺滑靠动画层的固定 stagger，不靠 flush 频率」——MP 在 `research-streaming-smoothness` 里独立做出来了，而且不只是解耦，是把坨状到达**填平**成连续打字。**这条该进 §三 领先项，不该进洞。**

**底层还剩的**：`StreamingMarkdownSource.observe()`（`:59-75`）在 `vm.streamingText` 每次变化时 yield 完整快照，渲染侧每份完整重 parse（fork 协议注释自述 "re-parses each snapshot"）。09-02 真机实测一条回复期间 `CardFlowView.body` 重建 **937 次**（`docs/research-input-jank.md`，已标为 B3 老病、**单独立案**）。这是 CPU/电量成本，随长度线性增长；用户看不到，因为节拍器在前面挡着。

**Minis 的阶梯节流**（<500 字 0.2s … 以上 2s + 换行快车道）仍是 B3 的参考解法之一——但 MP 的落点不同：节拍器已经是 flush 与显示之间的缓冲层，节流该加在**节拍器上游**（yield 点）而不是显示侧，否则会跟 30Hz 追赶打架。**不紧急，跟着 B3 走。**

**车头记账**：kimi 在 L3 报告里明确标了「ChatBubbleStyle 节奏器本次未目读，标未查证」，车头收货时没有去验这一条就把它写成了洞。这是本批次 §一 里唯一一条被推翻的。

## 三、MP 已经领先的（别改）

六轴的反向发现合并去重。这节的作用是**划出不该动的地盘**——对照一个更成熟的项目时最容易犯的错，是把自己的正确选择也一起推翻了。

> **09-08 补记**：08-24 之后新长出的领先项——桌面小组件 `MemoryPalaceWidget/UsageWidget.swift`（Minis 的 Widget target 只承载 Live Activity）；权限三档 + askOnce 弹卡（`PermissionPromptCenter.swift` 注明「OpenMinis OffloadPermissionManager 同构，按 MP 架构原生实现」）；`run_command` 的 envelope / 有界收集 / 头尾截断按 Minis 档案做但修了它「超时当空结果」的反面教材（`RunCommandTool.swift`、`DeviceToolSupport.swift:4-5`）。两家 09-01 同一天都把 iSH 子模块推上 master。

### 对象模型

1. **楼层是比它的 workspace 更完整的产品边界。** Minis 的 workspace 实为 `<sessionId>/workspace/` 会话文件桶，它的 Soul 反而是全局单份。MP 一个 Profile 绑定名称、人称、system prompt、模型、preset、历史、WorldBook、文件库——这是长期关系的容器。**不要用 workspace 换楼层。**
2. **树内分支明显领先它的 fork。** Minis 的消息没有 parent/children（只有 `sessionId` + `sortOrder`），`SessionForkManager` 只有两个整会话拷贝 API，没有树内兄弟、没有合并、没有对比。MP 的分支在产生、修复、导航、UI 切换、整树复制五处都理解这棵树，**同步入站还会对 `childrenIds` 取并集**（`SyncStore.swift:567-575`）——两端各自长出的分支能共存。
3. **preset 插槽表达力强于 Soul，而且不算过度设计。** 记忆、用户画像、时间轴、文件库、世界书都真的在用这套槽位。唯一该改的是信息层级（见 §二 F 末条），引擎留着。
4. **有 Minis 没有的外部历史入口。** ChatGPT `conversations.json` 导入保留 mapping 树（`ConversationImporter.swift:35-59, 464-485`）。

### 数据安全

5. **删除语义比它完整，而且已经绕开了 `isDeleted` 保留名那个坑。** MP 是 `isTrashed` + 90 天永久墓碑 + 恢复纪元阻断老墓碑反杀（`Conversation.swift:37-47`、`SyncStore.swift:383-472`）；Minis 现在的政策是收到远端 delete 直接**硬删**本地 session 及 children/files，没有用户可见的跨设备回收站。
6. **有真正的时间点备份和可回滚导入链。** Time Machine 是活路径（`MemoryPalaceApp.swift:849-877`），`.mpb` 全量备份有 section checksum、导入前验证、两阶段替换、主位验证。Minis 的 sync/migration 是收敛系统，**不是**时间点备份（本轮在 `Agent/Sync` + `Agent/Session` 范围内没找到快照/还原点实现）。
7. **API key 是否同步 iCloud 交给用户选，Minis 是无条件 `kSecAttrSynchronizable = true`。** 凭据同步是隐私选择，MP 这条更对。

### Agent 机制

8. **`ask_user` 的暂停/恢复比它完整。** 整轮恢复参数 + 既有工具结果 + 题面打包进 pending 状态，答完落成真实 user 节点再把配对的 tool result 接回循环。Minis 的 iOS 工具定义里**没有 ask-user 这个工具**。不要重写成普通文本追问。
9. **工具海的 defer/meta-tools 已经领先。** 超 16 个换 `tool_search`/`tool_inspect`/`tool_invoke`；Minis 的 `makeAgentTools` 返回固定大 schema，没有目录式按需暴露。
10. **原生 MCP 调用链比它紧。** MP 直接建 transport/client 并渲染成模型原生 schema；Minis 是在 prompt 里教模型去 shell 跑 `minis-mcp-cli tools/call`——那是它「给 agent 一台 Linux」的产物，不是更好的设计。做 MCP OAuth 时要服务现有 native transport。
11. **美元预算单位 + 8 轮低总闸都比它合适。** MP 多 provider 多价位，USD 是对的单位（Minis 那个 `RequestBudget` 其实只管图片字节）；Minis 允许 200 个 agent turn，对手机陪伴客户端和私人 key 代价过高。**修漏账和 off-by-one，别抬总闸。**
12. **个人记忆的可审计性更适合陪伴产品。** 逐字 quote + source node + 机械校验 + 用户可编辑；Minis 的 daily memory 是模型把自由 Markdown 塞进当天文件。模块**运行质量**曾不健康（病历在案），但「来源锚 + 可编辑原子事实」这个**架构选择**是对的。

### 产品边界

13. **文件库的楼层隔离 + 根目录 containment 比它的全局挂载更贴定位。** Minis 把 global memory/skills/shared 三棵树直接做成 Files provider 顶层（虽设只读但默认可见）。
14. **「分享后能去哪」比它丰富。** Minis 最终只有填 composer / 加附件；MP 有聊天附件、书架、对话导入、贴纸包四套入口——所以 MP 的 Share Extension 该做**路由器**而不是单一漏斗。
15. **Push NSE 的边界是个好模板。** 不读整库，只读 App Group 里 `chat → profile → 名字/头像` 的轻量索引，查不到就 fallback。这种「给 extension 最小 DTO、不共享主数据库」比把整棵工作区塞进 App Group 更适合当 MP 新扩展的样板。
16. **cc-bridge 让 MP 避开了 Minis 最重的一笔架构债。** Minis 为本机 agent 长任务维护 audio/location/background/Live Activity 联动，有效保活依赖两个用户开关。MP 的重活跑在 hub 上——缺的是「提交已被接受」的持久合同，**不是**把 iPhone 变成常驻 agent 进程。

### 聊天界面

17. **键盘期的逐帧贴底滑动，Minis 架构里没有等价物。** MP 是焊帧 + 绝对值钉位 + 键盘真曲线 `UIView.animate`（`PagingViewController.swift:290-357`），效果从「一帧瞬跳」变成「连续 13 帧逐帧滑动」。Minis 是 SwiftUI 系统自动避让 + `inputFocused` 边触发一次延迟 0.3s 的回底滚动——键盘期正文根本不跟随。**这是重写最可能弄丢的东西。**
18. **输入条键盘绑定的结构更干净。** MP 用 UIKit `keyboardLayoutGuide.topAnchor` 直绑，键盘几何是约束真值；Minis 依赖 SwiftUI 自动避让 window 级生效，反被咬出 phantom inset（离开聊天页残留键盘 inset 顶起 home 按钮，被迫 `onDisappear` 强制 `endEditing`）和 zombie inset（后台快照期 inset 滞留，被迫按状态切 `.ignoresSafeArea(.keyboard)`）。
19. **没有死代码渲染路径。** Minis 的 KaTeX/WKWebView 数学方案全仓只剩一个 `warmUp()` 调用点，render 零调用——每次启动白预热一个离屏 WebView。
20. **流式顺滑靠节拍器，比 Minis 的「动画层 stagger」走得更远。** `StreamPacer` 把 provider 坨状到达（每 0.1-0.6s 一坨）解耦成 30Hz 连续打字，滚动期暂停吐字、补偿器滚动中不补。Minis 只是把 flush 频率和视觉顺滑拆开；MP 是把到达节奏**填平**了。（09-02 补，纠正洞 8 的误判。）
21. **macOS 覆盖本身就是资产。** 同一套 SwiftUI 列表两端可用，macOS 侧根本没有键盘避让这个战场。这既是领先项，也是「不该重写」最硬的论据之一。

### Provider 细节

22. **OpenRouter 缓存路由比它完备。** 稳定 `x-session-id` 钉会话 + DeepSeek 指定官方上游 + per-block cache 断点。Minis 只有通用 compat + 顶层 cache_control，**没有**上游 provider pinning。这条是拿真实故障换来的。
23. **未完成的 ChatGPT 登录能跨实例恢复**（verifier/state/authURL 带 TTL 持久化）；Minis 的 Codex flow 把这些留在一次调用的局部变量里。iOS 切后台场景 MP 更有恢复力。

## 四、明确不学的

### 别照抄它的形状

1. ~~**不逐家补齐 OAuth。**~~ **⧫ 已被粟粟推翻，见 §七。**（原判断错在把 OAuth 当功能对齐；实际有真实用户卡在门口。08-24 拍板暂且搁置。）
2. **不照搬「每品牌一个目录」。** 看着整齐，它自己也有重复 factory 和上千行的 `OpenAIAgentProvider`。按 wire/auth/transport 职责拆，不是把 12 个 OpenAI 兼容品牌复制成 12 套 SSE parser。
3. **不学它的注册表「假完成感」。** `SyncableTypeRegistry` 的 `resolveConflict` 和 apply closures 被构造了，但入站实际仍跳到手写 merger。MP 若建注册表，要让真实入站路径**只能**通过它，否则少一层抽象更诚实。
4. **不学多 transport 共用单个 dirty 确认位。** 它声称广播给多 transport，但任一路 success 就清全局 dirty——LAN 真上线时第一路成功会让第二路失去重试账本。**MP 从第一天就要 per-transport ack。**
5. **不学 V1/V2 长期混合双引擎。** 它的 V2 hydrator 还在回调 V1 的 provider secrets/merge 函数。用一次性 adapter 迁移，不双写。
6. **不学 `Voice/` 目录当 LLM provider 分层模板。** 那是独立 ASR/TTS adapter，MP 已有自己的通话状态机。

### 别降级我们的产品语义

7. **不用 daily log 换原子记忆。** daily log 回答「这个项目做过什么」，原子事实回答「这个人是谁」。要项目连续性就另加第三层 workspace memory，不混库。
8. **不用 workspace / fork 换楼层 / 分支树。**
9. **不学会话纯硬删。** 不因为 transport 简单就降级掉用户可恢复的回收站。
10. **不把 `SessionLockStore` 当数据加密或多设备编辑锁。** 它明确是 UserDefaults + 内存的 UI 门禁，不进同步不进导出。**现在也不需要分布式会话锁**——并发新消息用分支承接，同节点编辑用 node version，正在流式生成的 UI 用本机 activity gate 保护。

### 别把它的架构债搬过来

11. **不学静音音频 / 定位保活。** 它的 headless intent 在 await 前 eager arm，有效保活靠后台静音音频，plist 声明 audio/fetch/location/remote-notification。MP 的正确方向是 durable job，不是制造常驻 iOS 进程。
12. **不学 200 轮总闸和 10/20/30 循环阈值。**
13. **不学 skills 的远程递归导入 + 脚本执行。** 它有 Linux 沙箱兜底，MP 没有。**尤其不要把 CC 桥当 skill 执行器**（撞「cc 是 cc，自己的文件是自己的文件」铁律）。
14. **不学 guest OAuth token bridge。** 它为了让沙箱里的 daemon 自己刷新，把 access/refresh token 和 client credential 复制到 guest 可见的明文 JSON。MP 是原生 transport，token 留在 Keychain。
15. **不学一个 scheme 混装外部导航 + 内部资源 + 敏感参数。** 它的 `minis://` 同时服务资源 spec 和 share/session/settings router，还允许 env value 进 query；而且**它的 spec 和实现已经漂移**（spec 写「无跨 session 读」，resolver 实际扫所有 session 目录返回第一个命中）。
16. **不学全设备 `@` 扫描**（三层 mount、深度 3、预算 5000 项、10 分钟缓存）。MP 有文件库边界，只需要一个 `@文件库路径` 选择器。
17. **不学 `ListSessionsIntent` 把全部会话标题+ID 拼成大字符串。** MP 历史更多且有楼层边界，该让实体查询承担选择，需要机器消费时返回结构化实体集合并分页。
18. **不学 Share Extension 记录分享正文日志**（它写前 100 字），也不学从 responder chain 找 UIApplication 强开 URL。「暂存成功」和「是否打开主 app」应该解耦。
19. **不学默认把 memory/skills 暴露到 Files。**

### 聊天界面：别回头，也别搬创可贴

24. **不学 SwiftUI 自动键盘避让 + 按状态切 `.ignoresSafeArea(.keyboard)`。** Minis 为此打了一串补丁；MP 的 UIKit 直绑结构上更稳，别回头。
25. **不学三层高度缓存 + seed + content-keyed memo 体系。** 那是 UIKit self-sizing 的创可贴，不是可移植资产——不重写列表就永远用不上，重写时才以「伤疤清单」身份参考。
26. **不学 KaTeX/WKWebView 数学渲染**（Minis 自己已弃为死代码）。真要上数学，照它的现役答案想：SwiftMath 原生 + 调度器分批让出。
27. **不学 cell-per-block 拆分 + 4 种 CellRegistration。** 它绑定 diffable 架构存在；MP 的 segmented 渲染已在 view 层做了块拆分，不需要列表层配合。

### 伪差距，别为对齐立项

20. **Widget** —— 它的 Widget target 只承载 Live Activity，没有桌面小组件。真正的差距是 Live Activity（架构级）。
21. **File Provider** —— 现在不做。但顺手发现的 plist 真相源漂移值得单独收口（见 §二 C 组）。
22. **Retry Run 作为首批 App Intent** —— 那是它的 agent run 语义，不是 AI app 的通用入口。
23. **分布式会话锁** —— 见第 10 条。

## 七、Gemini / GCP：粟粟推翻后的重新查证（08-24）

> 粟粟：「其实我觉得他们 oauth 很好啊！😱之前还有我的用户问我 gcp 的事」
> 这条信息推翻了 §四 原第 1 条。以下是重新查证的事实链。

### 事实一：MP 现在的 Gemini 走的是 AI Studio 兼容端点

`APIProvider.swift:283-285` — `baseURL: "https://generativelanguage.googleapis.com/v1beta/openai"`，type 是 `.openaiCompatible`，靠用户自己去拿 API key。

### 事实二：官方 OAuth 解决不了「不碰 GCP」，反而强制要 GCP

Google 官方文档口径：走 OAuth 前必须先建 Cloud project 并在 Console 里启用 Generative Language API。
更关键的一条——`generativelanguage.googleapis.com` **没有**能换取「按用户 Google AI 订阅计费」的 authorize flow。
所以「用 Google 账号登录就能用 Gemini」这件事，官方路径给不了。

### 事实三：Minis 那条路是唯一绕开 GCP 的通道

`Providers/Gemini/OAuth/GeminiOAuthManager.swift`：
- 登录：标准 Google OAuth + PKCE(S256) + `access_type=offline`，回调走**本地 HTTP server** `localhost:8085/oauth2callback`（`:70-141`）
- scope 要 `cloud-platform` + userinfo.email/profile（`:26`）
- 拿到 token 后**自动把 GCP 那步做掉**（`:368-381`）：
  `loadCodeAssist`（发现已有 Cloud Code project）→ 失败则 `onboardUser`（**自动创建**并轮询 operation，最多 24 次 × 5s）→ 再失败用 Cloud Resource Manager 找第一个 active project
- 请求打的是 `cloudcode-pa.googleapis.com/v1internal`，请求头伪装成 Gemini CLI：`User-Agent: GeminiCLI/0.30.0 (darwin; arm64)`、`ideType: GEMINI_CLI`（`:28-33, 384-388`）

**这就是「用户全程不碰 GCP 控制台」的实现方式**：app 用 Gemini CLI 的身份替用户把 project 开通了。

### 事实四：这条路的三个真实代价（必须让粟粟知道再拍）

1. **开源版是残的**。`clientSecret = "GOCSPX-xxxxxxxxxxxxxxxxxxxxxxxxxxx"` 是占位符，注释写着「supply your own from Google Cloud Console」（`:21-24`）。MP 要用必须自己注册 OAuth client。
2. **敏感 scope 要过 Google 验证**。`cloud-platform` 是 restricted scope，未通过验证的 app 有 100 用户上限 + 授权页警告。上架产品要走 Google 的 OAuth 应用审核。
3. **`v1internal` 是私有端点 + 身份伪装**。这条路本质是白嫖 Gemini CLI 的免费额度，Google 随时可以关；对一个要上 App Store 的产品，这是需要粟粟自己判断的风险，不是工程能替她拍的。

### 三条候选路（等粟粟拍）

| 路 | 做什么 | 用户体验 | 代价 | 风险 |
|---|---|---|---|---|
| **A · 引导** | 不做 OAuth，把「去哪拿 Gemini key」做成 app 内引导：直达 AI Studio 正确页面、明说免费 key 不需要开 billing | 仍要自己拿 key，但不会迷路 | **小时级** | 无 |
| **B · Code Assist OAuth** | 抄 Minis 的机制，按 MP 架构原生实现 | Google 账号登录即用，全程不碰 GCP | **周级** | 私有端点 + 身份伪装 + Google 审核 |
| **C · 官方 OAuth** | 标准 Gemini OAuth | 仍要用户自建 GCP project | 天级 | 无风险但**没解决问题** |

C 可以排除——它要求用户碰 GCP，正是要躲的那件事。
A 和 B 不互斥，**A 可以先上**（小时级），B 作为正式方案排期。

## 八、消息列表该不该重写（专题）

Minis 的消息列表叫 `CollectionViewMessageListV3`——名字里的 CollectionView 和 V3 说明两件事：**它沉到了 UIKit，并且重写过至少两次**。MP 在 SwiftUI + LazyVStack 反转列表上流过大量血，所以这个问题必须正面回答。

### 结论：不该重写。

不是「现在没空」，是**证据指向换坑而非根治**。

### MP 的 8 条血泪教训，在 Minis 架构下还存在吗

| 坑 | Minis 架构下的状态 | 性质 |
|---|---|---|
| 1 SwiftUI geometry API stuck 0 | 列表层根治（V3 设计头第一条就是「唯一高度源 = UIKit self-sizing，不用 GeometryReader」），但列表**外**存活——Minis 自己被 GeometryReader+onChange 在 iOS 18 async renderer 上咬出 SIGTRAP，输入条高度要带四重防护（瞬态 0 守卫 / 离屏帧丢弃 / 同步 seed + 380ms 自校正 / debounce） | 半个根治 |
| 2 反转列表离底漂移 | **根治**——同帧补偿长在 layout 内部（`invalidationContext` 在同一个 layout pass 里写 `contentOffsetAdjustment`），不需要「万级估算重排」这种阈值启发式，因为高度源是确定性缓存表。**这是 8 条里最硬的一条根治** | 根治 |
| 3 动态 contentMargins 键盘期是毒 | 坑不存在——键盘从不碰列表 inset | 需求取消 |
| 4 键盘位移动画三路判死 | 坑不存在——**因为它没接这个需求**（键盘动画交给系统，只在 focus 变化后延迟 0.3s 补一次回底）。MP 在这条上领先 | 需求取消 |
| 5 按测量高度切分支振荡 | 列表层根治，但换成「就地变异 → 高度缓存陈旧」坑族，Minis 为此维护至少四套手工失效机制 | 根治但有对价 |
| 6 `_ConditionalContent` frozen | 列表层根治，cell 内存活——`.sheet`/`.contextMenu` 照样把 self-sizing 充气，workaround 是挂到零尺寸 `Color.clear` overlay | 半个根治 |
| 7 VStack 空白区 hit 穿透 | 一样存在，一样的修法（`Color.clear.contentShape(Rectangle())`） | 无关 |
| 8 探针扭曲测量 | 一样要面对，但 Minis 的基建更好（见 §二 G3） | 无关 |

**2.5 根治 / 2 需求取消 / 3.5 与架构无关。** 没有一条是「换架构就自然消失且零副作用」的免费午餐——而且两条「需求取消」是拿体验换的。

### 沉到 UIKit 换来的新坑族（MP 今天零暴露）

1. **`FB13213926` hosting-graph 崩溃家族**——UIKit 自测量重进 SwiftUI view graph 撞上 async renderer 拆图，至少 5 次坠机记录。防御是 `noff_try_objc` + `withExtendedLifetime` 钉住整棵 contentView 子树 + off-collection 守卫 + 交互/流式窗口短路 + `prepareForReuse` 里**不敢**清 contentConfiguration。**MP 的列表是纯 SwiftUI，对这套崩溃面零暴露；一旦把 SwiftUI 气泡塞进 UIKit 复用循环，这整个家族就是门票。**
2. **高度缓存陈旧族**——cell 侧、layout 侧、content-keyed memo 三层，任何 `@Published` 就地变化都要手工定向失效。
3. **suspend/resume 快照延迟链**——用户滚动即挂起流式 UI，于是需要 pending-snapshot + 三路 flush 兜底，每一块注释都是一次「UI 冻住/块丢失」事故。
4. **体量**：三个文件 **7260 行**（协调器 5131 + 基建 1130 + layout 999），而且这是**第三次**重写。

### 四条理由（按权重）

1. **要治的病都已经治了。** 8 条教训全部有已落地、经探针验证的修复。重写解决的是已解决的问题。
2. **证据指向换坑。** 见上两表。「V3」这个命名本身就是答案——沉到 UIKit 不是上岸，是换一片海继续游。
3. **MP 的主战场是 macOS，而 UIKit 列表不覆盖 macOS。** MP 两端共用源码，重写意味着要么 iOS 单独一套实现 + macOS 保留 SwiftUI（长期双维护），要么 macOS 也硬迁 NSCollectionView（自测量生态不对等，未知风险区）。**在主战场上买不到任何东西。**
4. **MP 在键盘轴上已经领先。** 重写最可能弄丢的恰恰是已经赢的部分：键盘逐帧贴底、StreamScrollAnchor、垫块法——全部要在新架构里重新等价实现并重新排雷。

### 重写的触发条件（哪天成立了再回来翻这一节）

- (a) 单会话消息量级长到 LazyVStack 的首屏/回翻成本变成用户可感的投诉；

## 一、边界情况

**输入异常**
- `mem_c2_every`：没写过 = 20；导入 / 手改出界的夹到 6–40（`FragmentWatch.every`）；步进器步长 2，奇数值照样能用。老键 `mem_extract_interval` 不迁移（单位是「轮」，换算不过来），所有人落到 20。
- `mem_c2_marks` 里坏掉的条目（缺 id / 时间）读的时候跳过，等于那个窗口「第一次见」：只记位置，不回头补。
- C2 模型输出：表的形状没动，严格 JSON / 重来一次 / 整包拒收照旧；新模板只改了说法。有自定义模板的人不覆盖（二级页显示「自定义」）。
- 审计台：没有 `sourceConversationId` 的条目不列窗口、没有「跳到这条」；出处节点被删了退回 `sourceQuote`，再没有写「没有出处」；窗口删了标题写「已删的窗口」；自己选的日期从 / 到反了也认；改字空的不存；类别不在五种里的照原字显示。
- 来源判定：v5 碎片池 = `importance != nil`。只有 C2 写这个字段（有单测）；改版前 = 不是碎片且建于 10-15 20:29 之前；之后手加 / 导入的只在「全部」里。
- 横条截止点：启动时记一次（`MemoryAudit.recordCutoffIfNeeded`）；没记到（理论上不会）就不出横条，不会误删。

**并发**
- `FragmentWatch` 是 actor：同一窗口同一时刻只认领一截，认领带 token，超时作废的旧任务落不了库、动不了水位（astra #1–#3）。API 窗口和 CC 窗口 id 不重叠，共用水位不会互相抢。
- 审计台、常驻页、记忆格都改同一个主 context：存成了才发 `.memoryDidChange`，其余两处收到就重读。常驻页的计算在后台另开 ModelContext，读的是已存盘的数据；存盘前不会发通知，所以不会读到半截。
- 切楼层：审计台 / 常驻页 / 记忆格在 `profileWillSwitch` 时清空；后台算回来的结果先核对楼层，换了就丢。
- 批量删：确认框打开时冻结楼层 + id 快照，执行时只删快照里仍活着、同楼层的（astra #6）。

**失败重试**
- C2：只有落库成功 / 合法空包 / 格式两次拒收才挪水位；断网、超时、写库失败放回，下一轮回复落地再来（astra #2）。
- 审计台 / 常驻页保存失败：顶上一行红字，不清选择、不发通知、横条不记「用过」（astra #7）；不 rollback（主 context 全 app 共用）。
- 短窗口：排队时判一次，`closeoutBody` 执行前按实际主线再判一次（astra #8）；「现在写」豁免。已经写了的短窗口 A2 / A3 不删。

**空状态**
- 审计台三段各自空状态（「没看过的都过完了」等）；筛完一条都没有也走这个。
- 常驻页一条都没有：上半一行「现在没有每一轮都带的记忆。在记忆列表里左滑一条「钉住」，它就会到这里」，下半照常（可能也是空的那句）。
- 记忆格顶上那一行 N 可以是 0，照样能点进去；搜索时整行藏起来。
- 【开窗口】C 没勾：常驻页档案那组照样列、全灰「C 没勾，现在不带」；下半不出档案段。

## 二、和下一模块的交互风险

- **C3 接审计台**：审计台的数据源是 `Memory` 表（一次 `listAll`）。C3 按 v5 写的是点 md + 分层索引，不往 `Memory` 写——接进来要么给审计台加第二个数据源，要么 C3 结果落一份 `Memory`。`MemoryAudit.Origin` 已经留了枚举位，但「留 / 删」的语义（`reviewedAt` / `supersededAt`）是 `Memory` 字段，C3 条目没有对应字段。另外：真有第二个写手往 `Memory.importance` 写，「v5 碎片池」的判定就不准了，到时要加来源字段。
- **C 默认不勾 + 召回侧**：没动过这一勾的人，档案整段不进 prompt，「想起来」只剩召回工具（`RecallTool` 不看这一勾）。召回侧怎么排、标失效的会不会被召回，决定了她感受到的「AI 还记不记得」。审计台「删」= 标失效：召回默认只搜活着的（`RecallTool.swift:380-382` 走 `listActive`），但模型可以带 `includeInvalid` 把失效的也搜出来（标「（已失效）」）——审计台删掉的垃圾碎片仍可能被这样翻出来，召回侧改动时要记得。C3 做好后要有人记得把 C 的默认改回来（或给老用户一个提示），否则这一勾会一直关着。
- **常驻规则跟检索开关耦合**：
  - `MemoryResident.archiveRule()` 直接取 `activeRetrievers()` 里那一路 `PersistentRetriever` 的判定。以后改检索器组队、改 `isPersistent`，常驻页和记忆格「从聊天里记住的」会自动跟着变（这是好处），但也意味着改检索开关 = 记忆格的列表会变（关系 / 偏好会在常驻页和普通列表之间挪）。
  - `InjectionPreviewSections.volatileTitle` 按「有没有 `KeywordRetriever` / `VectorRetriever`」判第二段标题；加新的检索器类型（tag 等）要记得在这里归类。
  - 「带没带」靠 `InjectionHit.retrieverId` 的字面量 `"persistent"` / `"fullFallback"`；改这两个字串常驻页会全变灰。
  - {助手}的记忆那组靠 `SelfMemoryInjection.fullCandidates` + `Built.fullSlugs`，和实发同一个函数；改 B4 注入规则时常驻页自动跟。
- **说明书**：facts 已写；`npm run rewrite` / `build` 没跑（要调模型），页面还没生成。

## 三、技术债

- astra #4（见上表）：写库与水位非事务，中间被杀最坏多一条换说法的重复碎片。
- 积压不足 N 条的尾巴要等再攒够 N 条才写（默认 20），比旧逻辑（每 3 轮 / CC 每 6 条）晚；窗口聊完不到 N 条的那截永远不写，除非以后聊满。
- 写库前查认领到真正落库之间有极小窗口未加锁（需恰好跨 15 分钟超时）。
- 保存失败不 rollback，界面对象已改但未落盘，之后 autosave 可能再存上。
- 改了 `Memory` 字段 → 全局备份指纹变，老 build 导出的包本来就按 appBuild 拒。`Memory.feedbackDownCount` 不在 `FullMemoryDocument` 里（改之前就有，`compareMemory` 本来就会报，没有测试跑整套覆盖检查）。
- API 那条路（`ConversationViewModel.extractMemoriesIfNeeded`）是 VM 私有方法，没有单测；「不再首轮必跑」只靠 `FragmentWatch` 的单测间接锁。
- 记忆格每次 `refreshMemories` 都在后台多跑一遍 `MemoryResident.summary`（`roundInputs` + 注入组装）；`roundInputs` 里还会再读一遍{助手}的记忆文件（`MemoryService` 当时不能改，没把已读的那份传进去）。主线程不碰盘（有单测），但多花一点后台时间。
- `MemoryResident.reason` 用的是视图层的 `MemoryCardView.categoryLabels`（`MemoryInjector.categoryLabels` 是 private，两份同样的表）。
- 审计台展开原话：按 `sourceNodeId` 在主线程取一条 `MessageNode`（`fetchLimit 1`，没加楼层条件，靠 id 唯一），每次展开一卡取一次；没缓存。
- 审计台信息行日期用的是现有 `MemoryDateText.short`（「10月15日」），plan 例子写的是「10-15」。
- 常驻页两个组头（「每一轮都会带的」「下一轮会看见什么」）是没有行的空 Section，insetGrouped 下间距可能偏大，等截图定。
- mac：常驻页从记忆格推入走记忆格那个 NavigationStack，可能盖住整列（以前踩过）；常驻页行上只有右键菜单，没做悬停 ⋯（已定不做）。
- 审计台在记忆 app 底栏里时，多选和记忆格读写同一份 editMode（按代码推断）；切格会退出多选。没在界面上验证过。
- `MemoryAuditPage.onClose` 现在没有调用方（弹层拿掉后留着参数，没传）。
- `docs/MODULE_INDEX.md` 还列着已删的 `MemoryHygiene.swift`（自动生成，等脚本重跑）；`manual` check 唯一硬错是 `00-start/connect-model.md` 引用的 Onboarding 文件已删，与本单无关。
- **只编过、没在界面上看过**：审计台（设置推入 / 底栏一格 / 筛选弹层 / 卡片展开 / 批量底栏）、常驻页、记忆格顶上那一行、底栏四格 + 每格左上齿轮 + 设置 sheet、开窗口页 C 那行小字、C2 二级页步进器。390 宽溢出、mac 设置窗、mac 记忆面板都没走过（todo 20）。

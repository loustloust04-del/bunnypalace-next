## 1. 一句话

翻页动画期主线程忙砍半（0↔1 −53%）、开对话主线程忙 −33~−38%、翻页/开对话落定后尾工 −95%；翻回列表的落地卡顿经 C5′ 修到比原版还好（最大帧间隔 60→46ms）；剩下的代价是舞台模式下 0↔1 落地那一帧 ~40ms（原版 ~20ms），「到能用」晚 ~15–25ms；冷启动没降。

## 4. 没做到的 / 已知问题

1. **冷启动没降**：~670ms 是 pre-main + App.init（~100ms：字体注册 27、主题 22、钥匙串）+ 三页首建 + 首帧一整块。唯一有效的 L4 把代价挪到了首次滑列表，不划算。钥匙串延后（L5）被 astra 判为有迁移顺序风险没做。
2. **舞台模式下落地那一帧变重**（astra R3 M1 取证结论）：新加的 `worstGapEndMs` 显示最大帧间隔恰好结束在「到能用」那一刻 → 卡的是**落地后第一帧**，不是动画中途、也不是测量伪影。Time Profiler 按新加的落定段 signpost 切：
   - 1→0：每次翻回列表都在落地帧里重刷列表 → **C5′ 挪到下一帧**，落地帧从 ~67ms 降到 ~46ms（原版 ~60ms，原版的大头在动画中途）。
   - 0↔1 仍剩：落地帧 ~40ms（原版 ~20ms），多出来的是 SwiftUI 整图更新 + 显示列表渲染（每次落地 ~30ms vs 不开舞台 ~10ms），app 层没有单个可砍的函数——是舞台把「每帧摊着做」的布局攒到落地一次做的结构性代价。换来的是动画期每帧轻了一半（0↔1 −53%）。到能用 0→1 +24ms、1→0 约 +18ms（C5′ 后）。
   - 粟粟手摸反馈（C5 前）「微卡，比老版好点」。
3. **1↔2 翻页只降 ~5–10%**：滑动的是 page2 自己，里面 ~135 个嵌套托管视图逐帧重排。要么开快照（有取舍），要么 page2 内部减负——都是下一轮。
4. **真手指测试没跑成**：`PerfFingerFlipUITests` 已写好，😷 上 XCUITest 报「Timed out while enabling automation mode」——需要粟粟在手机「设置 → 开发者 → 启用 UI 自动化」或确认一次授权，属于系统设置我不动。所以终测数字全来自合成驱动（CADisplayLink 开环按时间写 contentOffset，走真 `scrollViewDidEndDecelerating → finishPaging` 路径）。

## 4a. 第二轮（09-28 白天）：翻页逐帧整图更新的真凶

- **取证**：setNeedsLayout 调用栈采样 + astra R6 独立静态取证。舞台模式下挪动的页面仍每帧触发 SwiftUI `updateTransform → invalidateTransform`（页面用 UIView.transform 挪，SwiftUI 逐帧跟踪自己在窗口里的位置）；1↔2 另有窗口根宿主每次 ~115 次图失效。astra 的 `pageOffset` 假设实测否决。
- **R6 刀（默认开）**：列表页 / 聊天页挪动改写 backing layer 的仿射变换，绕开 UIView setter 的几何通知；page2 仍走 UIView（它走 layer 时落地要补算整页）。😷 三轮：**0↔1 动画期主线程忙 104→19 / 103→21ms（−80%）**，到能用 / 落定 / 最大间隔持平；1↔2 与之前一致。
- **C6 收尾（astra R7）**：停在 page2 时聊天页被 layer 挪在 −W，期间几何通知会让 SwiftUI 记住错位；改为所有收尾路径落定后下一帧经 UIView setter 对齐一次，layer 只在舞台 / 非宽屏 / 非减弱动态 / 非 VoiceOver 时用。全场景 ABBA（键盘修复包 vs C6，各 8 进程）：0↔1 动画期忙 129→37 / 124→33（−71/−74%），总忙 −52%，开对话 −5%；代价 0↔1 落地最大帧间隔 41→49 / 42→59、到能用 +6/+13ms（落地时页面已停，肉眼看不到，粟粟手摸定）。
- **1↔2 还剩 ~170ms**：全是 page2 自己被挪动引起的整页更新。page2 也走 layer 能降到 37–68ms，但落地补算 +25ms、到能用 +50ms——要两头都要得改 page2 内部，下一轮。

## 4b. 夜里漏掉、白天修掉的回归
